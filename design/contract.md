# Контракт данных

Единственный источник формы данных для сервера, интерфейса и тестов. Поля совпадают с моками прототипа `design/cqa-v3/index.html` (`CL0`, `D`, `AP`), поэтому интерфейс получает данные с сервера без переделки. Меняет файл только оркестратор (защищённый путь).

## Checklist

```json
{
  "version": 3,
  "rules": "Общие правила чек-листа: N/A только где разрешён, за время ответа не штрафуем, ...",
  "sections": ["Начало и понимание запроса", "Безопасность и решение", "Ведение и завершение диалога", "Грубые нарушения"],
  "criteria": [
    {"id": "01", "sec": 0, "name": "Установление контакта", "type": "bool", "w": 10, "na": false,
     "text": "Да — оператор поздоровался на языке клиента и представился в первом ответе.", "channel": "all"},
    {"id": "04", "sec": 1, "name": "Корректная и полная консультация", "type": "scale", "w": 20, "na": true,
     "naCond": "Чат закончился до того, как клиент сформулировал запрос.", "signal": "resolution",
     "steps": [20, 15, 10, 5, 0], "stepText": {"20": "...", "15": "...", "10": "...", "5": "...", "0": "..."},
     "text": "Оцените ответ или следующий шаг по шкале.", "channel": "all"},
    {"id": "08", "sec": 3, "name": "Грубые ошибки", "type": "flag", "w": 0, "signal": "risk",
     "questions": [{"k": "insult", "label": "Оскорбление клиента", "text": "..."}],
     "text": "Каждый вид нарушения — отдельный вопрос к модели.", "channel": "all"}
  ]
}
```

- `type`: `bool` (yes, no, na), `scale` (одна из `steps`, или na), `flag` (подвопросы, баллов не даёт).
- `w`: вес до перераспределения N/A. Сумма весов может отличаться от 100, итог всё равно нормируется.
- `signal`: пусто, `resolution` (метка «без следующего шага» и плитка аналитики) или `risk` (грубая ошибка).
- `channel`: `all`, `chat` или `call`. Критерий с каналом `chat` или `call` MUST иметь `na: true`, иначе `PUT /api/checklist` отвечает 422. На диалоге другого канала он получает `a: "na"` без вызова модели, `why`: «Критерий для другого канала».
- `call`: необязательное уточнение для звонка, строка или `null`. Модель получает его после `text` только на диалоге с `ch: "call"`, запрос по чату не меняется. Так чек-лист для чатов адаптируется к устной речи без отдельного критерия. Смена `call` пересчитывает только звонки.
- `jev`: необязательное исходное определение вопроса в формате Jev (`{type: "noul" | "choice" | "score", instructions, criteria, min?, max?}`) — так чек-лист импортируется и экспортируется в редакторе. Описания вариантов из `jev` заменяют в запросе «да», «нет» и «неприменимо»; при `jev: null` запрос и отпечаток не меняются.
- `rules` правится в редакторе чек-листа так же, как критерии: сохранение создаёт новую версию, смена правил — смена смысла всех критериев.
- Версии неизменяемы: сохранение черновика создаёт `version + 1`.

### Экспорт чек-листа и разница версий

- Любую сохранённую версию сервер отдаёт файлом: `json` (Checklist как в `GET /api/state`), `csv` для Excel (UTF-8 с BOM, разделитель `;`, строка на критерий, заголовок по-русски, без версии и правил), `md` (документ с правилами) и `html` (самодостаточная памятка оператора для печати A4, весь текст экранирован). Доля критерия в итоге указана «при всех применимых»: перераспределение веса N/A заранее не известно.
- Разница `{rules_changed, added: [{id, name}], removed: [{id, name}], changed: [{id, fields: [{field, from, to}], reevaluate}]}`. `reevaluate: true` — изменено поле смысла или `call` (`call` — новая оценка только звонков); вес, название, раздел и сигнал — `false`, итог пересчитывается без модели. Раздел в `fields` сравнивается по названию. При `rules_changed` заново оценивается весь чек-лист.
- «Что изменится» в редакторе отправляет черновик `POST /api/checklist/diff` и показывает Markdown: разницу считает только сервер.

## Dialog

```json
{
  "id": "p4-ru-002", "title": "Звонок p4-ru-002", "ch": "call", "lang": "RU", "dur": 620.4, "at": "07.11 13:49",
  "lines": [
    {"n": 1, "t": 12.3, "ts": "2026-...T13:49:43.1234567+05:00", "who": "client", "text": "Алло.", "s": 9.1, "seg": "conv"},
    {"fold": true, "from": 19, "to": 57, "t0": 120.0, "t1": 545.0, "label": "Удержание и разговор с коллегой"}
  ],
  "res": {"<criterion id>": "CriterionResult"},
  "reviewed": false,
  "cost": {"calls": 10, "verifier_calls": 1, "usd": 0.0121, "ms": 41000}
}
```

- `cost` — сумма по последней оценке диалога: вызовы основной модели, запросы второго мнения, цена в долларах и время. Это «стоимость одной оценки с учётом всех вызовов» из задания; интерфейс показывает её как есть. Цена второго мнения входит только сюда, по критериям она не делится: `CriterionResult.cost` — только основная модель.

- `ch`: `chat` или `call`. Для чата `t` — строка `MM:SS` как в источнике. Для звонка `t` равно `s`, началу реплики в записи, чтобы время в расшифровке совпадало с плеером; если `s` нет, `t` — секунды от первого события. `dur` есть только у звонка, в секундах.
- `at`: для звонка дата и время первого события, для чата время загрузки набора (в данных чата даты нет).
- `fold` стоит в `lines` перед первой свёрнутой репликой; сами реплики участка остаются в `lines`. Интерфейс сворачивает участок по `from`–`to` и может его раскрыть.
- `dup: true` — необязательный признак повтора реплики распознаванием. Реплика не удаляется.
- `lines` может быть `null`, если расшифровка ещё не загружена (так в моках прототипа); от сервера после загрузки всегда приходит список.
- `ts`: исходная метка без изменений. `n`: номер реплики с 1 в порядке источника.
- `s`: секунда начала реплики в аудиофайле (только звонок): метка стоит в конце реплики, паузы записи вычтены, сдвиг файла учтён.
- `seg`: `pre` (до оператора), `conv` (оценивается), `internal` (разговор с коллегой, удержание), `after` (после конца разговора). Свёрнутые участки описывает объект `fold`.
- `who`: `client`, `operator`, `bot`, `system` (из поля `speaker` организаторов; имя поля как в прототипе).

## CriterionResult

```json
{"a": 15, "alt": 10, "ev": [9, 10], "seg": "реплики 30–32", "why": "Обоснование по-русски.",
 "quote": "дословный фрагмент на языке диалога", "tag": "Не назван срок ответа",
 "better": "Как сказать лучше.", "evFail": false,
 "model": "qwen3-6", "calls": 1, "cost": 0.0012, "ms": 2100}
```

- Ожидание оценки — это отсутствие записи критерия в `res`, отдельного поля нет. Итог считается без таких критериев, интерфейс показывает «Ждёт оценки».

- `a`: ответ основной модели: `"yes"`, `"no"`, `"na"`, ступень шкалы (число) или для флага объект `{"insult": false, ...}`.
- `alt`: ответ второго мнения той же формы, если второе мнение включено. Для флага `a` — объединение основной модели и второго мнения (нарушение есть, если его нашла любая), а `alt` — ответ второго мнения как есть.
- Готовые ответы переиспользуются по смыслу критерия, общим правилам и тексту диалога; модель и версия промпта в этот отпечаток не входят, поэтому переключение сценария не пересчитывает набор. Поле `model` показывает, кто ответил. `make eval` вызывает оценщик напрямую, мимо сохранённых ответов.
- `ev`: номера реплик-оснований, можно системное сообщение. Для пропущенного действия пусто, а `seg` называет участок.
- `tag`: короткая причина снижения для группировки в аналитике. `better`: пример лучшей реплики для обучения.
- `evFail`: основание не прошло проверку после повтора, ответ помечен «на проверку».

## Appeal

```json
{"id": "a1", "kind": "appeal", "dlg": "call-024", "cid": "04", "from": 15, "ask": 20, "to": null,
 "ev": [30], "by": "Оператор", "at": "07.11 15:10", "status": "pending",
 "comment": "Комментарий заявителя", "reviewer": null, "reason": null, "decidedAt": null}
```

- `kind`: `appeal` (оспаривание оценки) или `review` (решение проверяющего по расхождению моделей или проваленному основанию). Поле `ask` есть только у `appeal`.
- Флаг тоже оспаривается и решается: для критерия `type: "flag"` поля `from`, `ask` и `to` — объекты `{"<k>": true | false}` по всем вопросам флага. Итог флаг не меняет. Очередь, фильтр «Грубые ошибки» и аналитика берут флаг с учётом последнего решения.
- `status`: `pending`, `confirmed` (оценка оставлена), `changed` (оценка изменена на `to`), `closed` (критерий изменён или удалён новой версией чек-листа).
- `reason` обязателен при решении. Исходный `res` не меняется никогда: итог считается с учётом последнего решения.

## Итог

Итог = 100 × Σ(вес × доля) / Σ(вес применимых критериев), доля: да 1, нет 0, шкала — ступень / максимум. N/A и `pending` исключаются, флаги в сумму не входят. Округление только итога, до двух знаков, половина вверх. Векторы проверки: `tests/fixtures/scoring_vectors.json` (77,69 и 82,94 из прототипа).

Ссылки организаторов на записи подписаны и живут около часа, поэтому в браузер они не уходят: интерфейс ходит только в `/audio` и `/player`. Сервер хранит `audio_url` в колонке таблицы `dialogs` и не отдаёт её ни в одном ответе. Если ссылку получить не удалось, `/audio` отвечает 502.

`POST /api/datasets` и `/upload`: битые записи входят в `skipped`, их идентификаторы и причины пишутся в журнал сервера.

`PUT /api/source`: ссылка API организаторов из интерфейса. Нужен `https://`, иначе 422; сбой API организаторов — 502, прежняя ссылка остаётся. Сервер хранит ссылку в базе, она важнее `CQA_ORG_API_URL`, в том числе для `POST /api/datasets`, и не уходит ни в один ответ. Сервер забирает сохранённый `group_id` при старте и раз в 5 минут, новые диалоги добавляются, дубли по `id` пропускаются, оценка сама не запускается.

`source` в `GET /api/state`: `null`, пока ссылки нет, иначе `{"group_id": "DEV", "synced_at": "<ISO>", "added": 0, "skipped": 65, "error": null | "<текст>"}`; до первого прохода после старта есть только `group_id`.

Ручной ответ — новый результат пары: итог берёт последний результат, запуск оценки пару с результатом пропускает, прежний ответ модели остаётся в базе. Для флага `a` — `{"<k>": true | false}` по каждому вопросу, для остальных — значение из `allowed_answers`, иначе 422. Апелляция на рассмотрении или решение по паре текущего смысла — 409: решение важнее ответа.

`PUT /api/config` применяется без перезапуска: сервер пересобирает оценщик, `mode` в состоянии меняется сразу; во время запуска — 409. Значения хранятся в базе поверх `.env` и переживают перезапуск. Пустой `jev_api_key` или `key` провайдера оставляет сохранённый ключ; ключи не уходят ни в один ответ. Ошибка конфигурации (нет ключа для `live`, неизвестный профиль, Jev без ключа, адрес не `http(s)://`) — 422, режим не меняется. Интерфейс открывает окно режима по клику на плашку `mode`.

`mode` описывает режим данных для плашки в интерфейсе: `{"where": "kz" | "local" | "external", "anonymized": true, "model": "qwen3-6", "verifier": "jev" | "self" | null}`.

## Провайдеры моделей (llm-evaluation)

Несколько OpenAI-совместимых моделей, у каждой свой ключ. Раздел уточняет `GET /api/config` и `PUT /api/config` из таблицы HTTP API: `PUT /api/config` выбирает провайдера, адрес и ключ модели задаёт `PUT /api/providers/{id}`.

Provider: `{"id": "deepseek", "label": "DeepSeek", "base_url": "https://api.deepseek.com", "model": "deepseek-chat", "profile": "plain" | "deepseek", "where": "kz" | "local" | "external", "has_key": true}`. `id` — строчная латиница, цифры и дефис, до 32 знаков. Провайдер `env` есть всегда: он собран из `CQA_LLM_*` и `CQA_DATA_WHERE` (и полей, сохранённых прежней формой режима) и меняется только в `.env`.

| Метод и путь | Тело | Ответ |
| --- | --- | --- |
| `GET /api/config` | — | поля из таблицы HTTP API и `llm_provider` (код основной модели), `providers: [Provider]`; `llm_base_url`, `llm_model`, `llm_profile`, `has_llm_key`, `data_where` описывают основную модель |
| `PUT /api/config` | `{llm_provider, verifier: "jev" \| код провайдера \| null, evaluator: "llm" \| "jev", anonymize, jev_api_key, allow_real_data}` | то же, что `GET /api/config`, после применения |
| `PUT /api/providers/{id}` | `{label, base_url, model, profile, where, key}` | то же, что `GET /api/config`: провайдер создан или изменён |
| `DELETE /api/providers/{id}` | — | то же, что `GET /api/config` |
| `POST /api/providers/{id}/check` | — | `{ok: true \| false, ms, error: null \| "<текст>"}` |

Ключ только записывается: ни в ответах, ни в журнале его нет, есть `has_key`; пустой `key` при изменении оставляет сохранённый. Список провайдеров хранится в базе и заменяет `CQA_PROVIDERS` из `.env`.

Провайдер `openrouter-jev` (Jev Router через OpenRouter) есть всегда, вторым после `env`: `{"label": "OpenRouter — Jev Router", "base_url": "https://openrouter.ai/api/v1", "model": "typesafe/jev-router", "profile": "plain", "where": "external"}`, ключ — `CQA_OPENROUTER_API_KEY` или `PUT`. `PUT /api/providers/openrouter-jev` меняет только `model` и `key`, остальные поля тела игнорирует; `DELETE` не удаляет, а возвращает его к умолчанию (409 — как у других, если он выбран). Если провайдер возвращает `usage.cost` (OpenRouter), `cost` — эта цена, а не цена за токены.

Основная модель — провайдер `llm_provider`: его `where` становится `mode.where`, `model` — `mode.model`. `verifier`: `"jev"`, код провайдера (те же вопросы по критериям уходят модели этого провайдера, её ответ — в `alt`) или `null`; `mode.verifier` повторяет его, поэтому в `mode` бывает и код провайдера.

Ошибки: неизвестный провайдер в `llm_provider` или `verifier`, нет ключа для `live` — 422, режим не меняется. Неверный `id`, адрес не `http(s)://`, неизвестный профиль, `PUT /api/providers/env` — 422. `DELETE` основной модели, второго мнения или `env` — 409, неизвестный `id` — 404. Любое изменение во время запуска — 409, как у `PUT /api/config`.

`POST /api/providers/{id}/check`: один запрос `max_tokens: 1` с синтетическим текстом «Ответь одним словом: да», без повторов, таймаут 20 секунд, реальные данные не уходят; запрос идёт в сеть и в режиме `replay`. Ошибка провайдера — `ok: false` с текстом, а не код HTTP; неизвестный `id` — 404.

## Режим «только Jev» (llm-evaluation, jev-only)

- `GET /api/config` отдаёт, а `PUT /api/config` принимает поле `evaluator`: `"llm"` (по умолчанию) или `"jev"`; в `.env` — `CQA_EVALUATOR`. Другое значение — 422.
- `evaluator: "jev"`: все критерии диалога отвечает Jev одним запросом (choice на критерий, noul на подвопрос флага). Языковая модель и второе мнение не вызываются, адрес и ключ модели не нужны. Без ключа Jev вне `replay` — 422 «Нет ключа Jev…», режим не меняется. Канал (`na` без вопроса) и обезличивание — как у языковой модели.
- `mode` в этом режиме: `model` — имя модели Jev (`"jev-latest"`), `verifier: null`.
- `CriterionResult` в этом режиме: `a` — ответ Jev; `why` — «Ответ Jev с вероятностью 0,93; модель не пишет обоснований» (у флага — наименьшая вероятность по вопросам), других причин нет; `ev: []`, без `quote`, `seg`, `tag`, `better`, `alt`; `model: "jev-latest"`; `calls: 1` у первого ответа диалога и `0` у остальных, `cost` — цена запроса поровну между ответами, `ms` — время запроса.
- Вероятность ниже 0,6 или её нет — `evFail: true`, ответ в «Нужна проверка»; карточка и очередь пишут «Jev не уверен в ответе». Флаг возвращается всегда: подвопрос без ответа — «не найдено» и `evFail: true`. Нет ответа по критерию — записи нет, критерий ждёт оценки. Сбой запроса — сбой всего диалога.
- `Dialog.cost` в этом режиме: `calls: 1`, `verifier_calls: 0`. `make eval` с `CQA_EVALUATOR=jev` оценивает эталон только Jev.

## Интонация звонка (dialog-ingest, prosody)

| Метод и путь | Тело | Ответ |
| --- | --- | --- |
| `GET /api/dialogs/{id}/prosody` | — | `{lines, speakers, summary}` — интонация звонка по звуку записи; 404 — чат, неизвестный id или звонок без записи; 502 — запись не получена |

```json
{"lines": [{"n": 12, "f0": 214, "range_st": 6.3, "db": 71.2, "wps": 2.6, "pause": 0.8, "flags": ["raised"]}],
 "speakers": {"client": {"f0": 180.0, "db": 66.0, "wps": 2.5, "lines": 30},
              "operator": {"f0": 110.0, "db": 65.0, "wps": 2.3, "lines": 28}},
 "summary": ["Клиент повысил тон в репликах 12–14", "Пауза 9 с перед ответом оператора (реплика 20)"]}
```

- `lines`: реплики клиента и оператора с `s`, в порядке расшифровки. `f0` — медиана тона, Гц; `range_st` — размах тона p10–p90, полутоны; `db` — средняя интенсивность речи, дБ по шкале записи; `wps` — слов в секунду речи; `pause` — тишина перед репликой после предыдущей реплики клиента или оператора, с. `null` — нет речи, тона или предыдущей реплики.
- Запись моно, говорящие различаются только по расшифровке: реплика кончается на метке `s + utterance_s(text)`, её речь — громкие кадры между концом предыдущей реплики и этой меткой.
- `speakers`: обычная манера говорящего — медианы `f0`, `db`, `wps` по его репликам с `seg` `conv` или без `seg`; `lines` — их число.
- `flags` ставятся только репликам `conv` (удержание и разговор с коллегой — `internal` — не оцениваются). Относительно манеры того же говорящего, если у него не меньше 3 реплик и реплика звучит не меньше 1,5 с: `raised` — тон на 3 полутона выше или на 6 дБ громче; `fast` — темп не меньше 1,5 обычного и 3,5 слова в секунду. Абсолютные: `monotone` — размах меньше 2 полутонов на реплике от 4 с; `long_pause` — ответ оператора клиенту после 5 с тишины и больше; `overlap` — реплика началась на 1 с и больше раньше конца чужой и позже её начала. Пороги эвристические, константы в `src/cqa/domain/prosody.py`.
- `summary`: фразы по-русски по флагам; подряд идущие реплики одного говорящего — диапазоном.
- Считается при первом запросе (свежая ссылка, скачивание в память, ffmpeg и Praat на сервере) и хранится в таблице `prosody`; 502 не сохраняется, следующий запрос пробует снова. Запись никуда не отправляется; в модель уходит только сводка (см. «Интонация в оценке звонка»).
- Интерфейс: карточка звонка запрашивает интонацию при открытии и показывает панель «Интонация» со сводкой и значки у реплик: `↑ тон`, `монотонно`, `быстро`, `пауза N с`, `перебивание`. Чат не запрашивает; 404 — панели нет; 502 — приглушённая строка «Интонация недоступна».

### Интонация в оценке звонка (llm-evaluation)

- Оценщик (`LlmEvaluator`, `JevEvaluator`, второе мнение) у звонка берёт разбор `dialog_prosody` (из таблицы `prosody` или считает) и добавляет блок `sound_block(summary)` после `</dialog>` (Jev и второе мнение — следом за репликами в тексте диалога): строка «Анализ звука записи (автоматически, по тону и громкости; распознавание речи не проверялось):», строки `summary` с «- » (пустая сводка — «- отклонений тона, громкости, темпа и пауз не найдено»), правило: тон, паузы и темп — по этим строкам, сверх них о звуке ничего, дикции и разборчивости по ним не оценить.
- Чат, звонок без записи, 404/502, нет ffmpeg или любая ошибка разбора — блока нет, запрос байт в байт прежний; системный промпт не меняется. Запрет реальных звонков (`CQA_ALLOW_REAL_DATA`) проверяется до разбора; в блоке только роли и номера реплик, без текста и имён.
- Отпечаток (`fingerprint`) звук не учитывает: появление интонации готовые ответы не пересчитывает, она входит в следующие оценки звонка. `make eval` идёт без интонации.

## Отчёт для руководства (eval-and-delivery)

JSON: `{at, filters: {lang, ch}, summary: {dialogs, scored, avg_total, risk: {dialogs, share, kinds: [{k, label, n}]}, no_next_step: {dialogs, share}, needs_review, open_appeals, cost: {dialogs, avg_usd, avg_s}}, criteria: [{id, name, n, na, share}], reasons: [{tag, dialogs, owner, criteria}], channels, langs: [{key, label, n, avg}], findings: [строка]}`. Ответы с учётом последнего решения, итог как в «Итог», доли от оценённых диалогов: `no_next_step` — ступень ниже верхней у `signal: "resolution"`, `needs_review` — не проверенные диалоги с расхождением или `evFail` без решения. `criteria` — средняя доля баллов без N/A, худшие первыми; `reasons` — топ-10 `tag` сниженных ответов; `findings` — 3–5 выводов по-русски из чисел, без модели. `html` — самодостаточная страница A4 для печати, данные экранированы; `md` — для вики и почты; без оценённых диалогов — «Нет оценённых диалогов».

## Доступ по токену (eval-and-delivery)

Пустой `CQA_ACCESS_TOKEN` — всё открыто, как раньше. Заданный: `GET /login?token=<токен>` — 302 на `/` и cookie `cqa_access` (HttpOnly, SameSite=Lax, path `/`), неверный токен — 401 со страницей входа без cookie. Без верной cookie `/api/*` — 401 `{"detail": "Нужен вход по ссылке с токеном"}`, остальные пути — 401, самодостаточная страница «Доступ по ссылке с токеном» без данных; `GET /api/health` открыт всегда. Сравнение — `hmac.compare_digest`, значение `token=` в журнале uvicorn заменено на `***`.

## Источники диалогов (dialog-ingest, sources)

Диалоги приходят из нескольких сервисов; у каждого диалога есть происхождение. `Dialog` получает поля `source_id` (id источника), `external_id` (id записи в источнике) и `product` (поле записи или `product_default` источника); дубли — по `(source_id, external_id)`. Диалоги организаторов и файла сохраняют `id` = `conversation_id`, у `http_json` и `webhook` `id` = `<source_id>-<external_id>`, название — «Чат <external_id>» / «Звонок <external_id>». `GET /api/state` получает `sources: [{id, name, kind, service}]` (без архивных) для фильтра и плашки источника.

Source: `{"id": "src1", "name": "Чат-платформа", "kind": "org_api" | "http_json" | "webhook" | "file" | "paste" | "api", "service": "ChatDesk", "channel_default": "chat" | "call" | null, "product_default": "Карты" | null, "config": {…}, "has_secret": true, "enabled": true, "schedule_min": 5, "created": "<ISO>", "archived": false, "ingest_path": "/api/sources/src1/ingest" | null}`. Встроенные: `org` (API организаторов, по умолчанию выключен, расписание 5 мин; прежняя ссылка `PUT /api/source` переносится в него), `file` (`POST /api/datasets/upload`), `paste` (`POST /api/dialogs/text`), `api` (интеграционный API). Встроенные не удаляются; у `file`, `paste`, `api` меняются только `name`, `service`, `channel_default`, `product_default`.

`config` (не секрет) по виду:
- `org_api`: `{"group_id": "DEV"}`; секрет — подписанная ссылка `https://…`. Включить без ссылки — 422.
- `http_json`: `{"url": "https://…", "method": "GET" | "POST", "auth_header": "Authorization" | "", "records_path": "data.items", "mapping": Mapping}`; секрет — значение заголовка. Логин, пароль или параметр вроде `token`, `key`, `signature` в адресе — 422 (адрес виден в интерфейсе).
- `webhook`: `{"auth": "bearer" | "hmac", "records_path": "", "mapping": Mapping}`; секрет — токен, его выдаёт сервер.

Mapping: пути (`agent.name`, `data.items.0`) к полям записи: обязательные `conversation_id`, `transcript` (список реплик), `speaker`, `text` (внутри реплики); необязательные `channel`, `language`, `timestamp` (внутри реплики), `audio_url`, `operator`, `product`, а также `speakers: {"<значение>": "client" | "operator" | "bot" | "system"}`. Роли и каналы понимаются по синонимам (`agent`, `customer`, `user`, `chat`, `call`, `voice`…); нет канала — `channel_default`; нет языка — по тексту; нет времени — `MM:SS` по номеру реплики.

| Метод и путь | Тело | Ответ |
| --- | --- | --- |
| `GET /api/sources` | — | `[Source]`, архивные с `archived: true` |
| `POST /api/sources` | `{name, kind, service, channel_default, product_default, config, secret, enabled, schedule_min}` | Source; у `webhook` ещё `token` — показывается один раз |
| `PUT /api/sources/{id}` | то же и `rotate_token` | Source; пустой `secret` оставляет сохранённый; `rotate_token: true` у webhook — новый `token` один раз; смена `kind` — 422 |
| `DELETE /api/sources/{id}?archive=true` | — | `{deleted}` без диалогов; есть диалоги — 409, с `archive=true` — `{archived}` (выключен, учёт и диалоги остаются); встроенный — 409 |
| `POST /api/sources/test` | поля `POST /api/sources` и `sample` | предпросмотр черновика, ничего не сохраняет |
| `POST /api/sources/{id}/test` | `{sample}` (для webhook) или пусто | предпросмотр сохранённого источника |
| `POST /api/sources/{id}/sync` | — | SourceSync: забрать сейчас (`org_api`, `http_json`); ошибка источника — `status: "error"`, не код HTTP; идёт синхронизация — 409; другой вид — 422 |
| `GET /api/sources/{id}/syncs?limit=50` | — | `[SourceSync]`, новые первыми |
| `GET /api/sources/stats` | — | `[SourceStats]` по всем источникам |
| `POST /api/sources/{id}/ingest` | JSON: список записей, одна запись или объект со списком по `records_path` | `{added, skipped, errors: [до 20]}`; `Authorization: Bearer <token>` или `X-CQA-Signature: sha256=<hex HMAC-SHA256 тела>` по `config.auth`; неверный — 401, выключен — 409, не webhook — 404, больше 10 МБ или не JSON — 422. Открыт и при `CQA_ACCESS_TOKEN` |

Предпросмотр: `{ok, error: null | "<текст>", ms, records, preview: [{id, external_id, title, ch, lang, lines, operator, product, sample: [{who, text}] × 3}] × 3, errors: ["<id>: <причина>"], paths: ["id", "agent.name", …]}`. Сбой связи — `ok: false` и текст без адреса (200). Ошибки настроек в любом вызове — 422 `{"detail": "Проверьте поля источника", "fields": {"config.url": "…", "config.mapping.text": "…", "secret": "…"}}`. Секреты не уходят ни в один ответ и журнал, есть `has_secret`.

SourceSync: `{id, source_id, started, finished, status: "running" | "ok" | "partial" | "error", added, skipped, errors: [..], duration_ms}`. Каждое поступление — строка журнала: синхронизация, webhook, файл, вставка, `POST /api/datasets`. `partial` — часть записей не разобрана, `error` — сбой целиком; прерванные перезапуском — `error` «прервана перезапуском сервера». Автосинхронизация: включённые `org_api` и `http_json` с `schedule_min > 0`, проверка раз в 30 с.

SourceStats: `{id, name, kind, enabled, archived, dialogs, scored, avg_total, gross_share, running: SourceSync | null, last_sync: SourceSync | null, syncs, error_rate, newest_at, freshness_s, health: "ok" | "warning" | "error", basis}`. Итог и грубые ошибки — с учётом решений, как в отчёте; `error_rate` — доля `error` среди последних 10; `freshness_s` — возраст самого нового диалога. `health` — первое сработавшее правило, `basis` — его текст: выключен — warning «источник выключен»; последняя синхронизация `error` — error «последняя синхронизация с ошибкой: <первая ошибка>»; `error_rate > 0,2` — warning «N% синхронизаций с ошибкой (последние 10)»; `partial` — warning «последняя синхронизация с пропусками: N записей не разобраны»; `file`, `paste`, `api` — ok «загрузка вручную» / «ошибок нет»; pull без синхронизаций — warning «ещё не синхронизировался»; нет данных — warning «данные ещё не поступали»; новый диалог старше 24 ч — warning «нет новых данных 24 ч»; иначе ok.

`http_json` ходит только в публичный интернет: адрес, который резолвится в частную сеть, loopback, link-local (169.254.169.254) и другие служебные диапазоны, — `ok: false` / `error` «адрес … во внутренней сети», перенаправления не выполняются. `CQA_ALLOW_PRIVATE_SOURCES=1` снимает запрет (источник в своей сети, `make demo`). Отчёт для руководства: `sources: [{key, label, n, avg}]` («По источникам»), фильтр `source=<id>`, `filters.source`.
