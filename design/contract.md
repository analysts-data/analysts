# Контракт данных

Единственный источник формы данных для сервера, интерфейса и тестов. Поля совпадают с моками прототипа `design/cqa-v3/index.html` (`CL0`, `D`, `AP`), поэтому интерфейс получает данные с сервера без переделки. Меняет файл только оркестратор (защищённый путь).

## Checklist

```json
{
  "version": 3,
  "rules": "Общие правила чек-листа: N/A только где разрешён, за время ответа не штрафуем, ...",
  "sections": ["Начало и понимание запроса", "Безопасность и решение", "Ведение и завершение диалога", "Грубые нарушения"],
  "criteria": [
    {"id": "01", "sec": 0, "name": "Установление контакта", "type": "bool", "w": 10, "na": false,
     "text": "Да — оператор поздоровался на языке клиента и представился в первом ответе.", "channel": "all"},
    {"id": "04", "sec": 1, "name": "Корректная и полная консультация", "type": "scale", "w": 20, "na": true,
     "naCond": "Чат закончился до того, как клиент сформулировал запрос.", "signal": "resolution",
     "steps": [20, 15, 10, 5, 0], "stepText": {"20": "...", "15": "...", "10": "...", "5": "...", "0": "..."},
     "text": "Оцените ответ или следующий шаг по шкале.", "channel": "all"},
    {"id": "08", "sec": 3, "name": "Грубые ошибки", "type": "flag", "w": 0, "signal": "risk",
     "questions": [{"k": "insult", "label": "Оскорбление клиента", "text": "..."}],
     "text": "Каждый вид нарушения — отдельный вопрос к модели.", "channel": "all"}
  ]
}
```

- `type`: `bool` (yes, no, na), `scale` (одна из `steps`, или na), `flag` (подвопросы, баллов не даёт).
- `w`: вес до перераспределения N/A. Сумма весов может отличаться от 100, итог всё равно нормируется.
- `signal`: пусто, `resolution` (метка «без следующего шага» и плитка аналитики) или `risk` (грубая ошибка).
- `channel`: `all`, `chat` или `call`. Критерий с каналом `chat` или `call` MUST иметь `na: true`, иначе `PUT /api/checklist` отвечает 422. На диалоге другого канала он получает `a: "na"` без вызова модели, `why`: «Критерий для другого канала».
- `call`: необязательное уточнение для звонка, строка или `null`. Модель получает его после `text` только на диалоге с `ch: "call"`, запрос по чату не меняется. Так чек-лист для чатов адаптируется к устной речи без отдельного критерия. Смена `call` пересчитывает только звонки.
- `jev`: необязательное исходное определение вопроса в формате Jev (`{type: "noul" | "choice" | "score", instructions, criteria, min?, max?}`) — так чек-лист импортируется и экспортируется в редакторе. Описания вариантов из `jev` заменяют в запросе «да», «нет» и «неприменимо»; при `jev: null` запрос и отпечаток не меняются.
- `rules` правится в редакторе чек-листа так же, как критерии: сохранение создаёт новую версию, смена правил — смена смысла всех критериев.
- Версии неизменяемы: сохранение черновика создаёт `version + 1`.

### Экспорт чек-листа и разница версий

- Любую сохранённую версию сервер отдаёт файлом: `json` (Checklist как в `GET /api/state`), `csv` для Excel (UTF-8 с BOM, разделитель `;`, строка на критерий, заголовок по-русски, без версии и правил), `md` (документ с правилами) и `html` (самодостаточная памятка оператора для печати A4, весь текст экранирован). Доля критерия в итоге указана «при всех применимых»: перераспределение веса N/A заранее не известно.
- Разница `{rules_changed, added: [{id, name}], removed: [{id, name}], changed: [{id, fields: [{field, from, to}], reevaluate}]}`. `reevaluate: true` — изменено поле смысла или `call` (`call` — новая оценка только звонков); вес, название, раздел и сигнал — `false`, итог пересчитывается без модели. Раздел в `fields` сравнивается по названию. При `rules_changed` заново оценивается весь чек-лист.
- «Что изменится» в редакторе отправляет черновик `POST /api/checklist/diff` и показывает Markdown: разницу считает только сервер.

## Dialog

```json
{
  "id": "p4-ru-002", "title": "Звонок p4-ru-002", "ch": "call", "lang": "RU", "dur": 620.4, "at": "07.11 13:49",
  "lines": [
    {"n": 1, "t": 12.3, "ts": "2026-...T13:49:43.1234567+05:00", "who": "client", "text": "Алло.", "s": 9.1, "seg": "conv"},
    {"fold": true, "from": 19, "to": 57, "t0": 120.0, "t1": 545.0, "label": "Удержание и разговор с коллегой"}
  ],
  "res": {"<criterion id>": "CriterionResult"},
  "reviewed": false,
  "cost": {"calls": 10, "verifier_calls": 1, "usd": 0.0121, "ms": 41000},
  "operator": "Алия К."
}
```

- `operator` — сотрудник, необязательное поле (нет поля — не указан). В записях организаторов его нет; источники по порядку: поле записи при загрузке (`POST /api/datasets`, `/upload`, автосинхронизация) — первое непустое из `operator`, `operator_id`, `agent`, `agent_id`, `agent_name`, `employee` (число — строкой); `PUT /api/dialogs/{id}/operator`; `POST /api/operators/import`. Повторная загрузка дописывает сотрудника только диалогу без него. Хранится в колонке `dialogs.operator`. Имя — данные пользователя: интерфейс и отчёты экранируют его, в запрос модели (и второго мнения, и Jev) оно не входит, обезличивание текста реплик прежнее.

- `cost` — сумма по последней оценке диалога: вызовы основной модели, запросы второго мнения, цена в долларах и время. Это «стоимость одной оценки с учётом всех вызовов» из задания; интерфейс показывает её как есть. Цена второго мнения входит только сюда, по критериям она не делится: `CriterionResult.cost` — только основная модель.

- `ch`: `chat` или `call`. Для чата `t` — строка `MM:SS` как в источнике. Для звонка `t` равно `s`, началу реплики в записи, чтобы время в расшифровке совпадало с плеером; если `s` нет, `t` — секунды от первого события. `dur` есть только у звонка, в секундах.
- `at`: для звонка дата и время первого события, для чата время загрузки набора (в данных чата даты нет).
- `fold` стоит в `lines` перед первой свёрнутой репликой; сами реплики участка остаются в `lines`. Интерфейс сворачивает участок по `from`–`to` и может его раскрыть.
- `dup: true` — необязательный признак повтора реплики распознаванием. Реплика не удаляется.
- `lines` может быть `null`, если расшифровка ещё не загружена (так в моках прототипа); от сервера после загрузки всегда приходит список.
- `ts`: исходная метка без изменений. `n`: номер реплики с 1 в порядке источника.
- `s`: секунда начала реплики в аудиофайле (только звонок): метка стоит в конце реплики, паузы записи вычтены, сдвиг файла учтён.
- `seg`: `pre` (до оператора), `conv` (оценивается), `internal` (разговор с коллегой, удержание), `after` (после конца разговора). Свёрнутые участки описывает объект `fold`.
- `who`: `client`, `operator`, `bot`, `system` (из поля `speaker` организаторов; имя поля как в прототипе).

## CriterionResult

```json
{"a": 15, "alt": 10, "ev": [9, 10], "seg": "реплики 30–32", "why": "Обоснование по-русски.",
 "quote": "дословный фрагмент на языке диалога", "tag": "Не назван срок ответа",
 "better": "Как сказать лучше.", "evFail": false,
 "model": "qwen3-6", "calls": 1, "cost": 0.0012, "ms": 2100}
```

- Ожидание оценки — это отсутствие записи критерия в `res`, отдельного поля нет. Итог считается без таких критериев, интерфейс показывает «Ждёт оценки».

- `a`: ответ основной модели: `"yes"`, `"no"`, `"na"`, ступень шкалы (число) или для флага объект `{"insult": false, ...}`.
- `alt`: ответ второго мнения той же формы, если второе мнение включено. Для флага `a` — объединение основной модели и второго мнения (нарушение есть, если его нашла любая), а `alt` — ответ второго мнения как есть.
- Готовые ответы переиспользуются по смыслу критерия, общим правилам и тексту диалога; модель и версия промпта в этот отпечаток не входят, поэтому переключение сценария не пересчитывает набор. Поле `model` показывает, кто ответил. `make eval` вызывает оценщик напрямую, мимо сохранённых ответов.
- `ev`: номера реплик-оснований, можно системное сообщение. Для пропущенного действия пусто, а `seg` называет участок.
- `tag`: короткая причина снижения для группировки в аналитике. `better`: пример лучшей реплики для обучения.
- `evFail`: основание не прошло проверку после повтора, ответ помечен «на проверку».

## Appeal

```json
{"id": "a1", "kind": "appeal", "dlg": "call-024", "cid": "04", "from": 15, "ask": 20, "to": null,
 "ev": [30], "by": "Оператор", "at": "07.11 15:10", "status": "pending",
 "comment": "Комментарий заявителя", "reviewer": null, "reason": null, "decidedAt": null}
```

- `kind`: `appeal` (оспаривание оценки) или `review` (решение проверяющего по расхождению моделей или проваленному основанию). Поле `ask` есть только у `appeal`.
- Флаг тоже оспаривается и решается: для критерия `type: "flag"` поля `from`, `ask` и `to` — объекты `{"<k>": true | false}` по всем вопросам флага. Итог флаг не меняет. Очередь, фильтр «Грубые ошибки» и аналитика берут флаг с учётом последнего решения.
- `status`: `pending`, `confirmed` (оценка оставлена), `changed` (оценка изменена на `to`), `closed` (критерий изменён или удалён новой версией чек-листа).
- `reason` обязателен при решении. Исходный `res` не меняется никогда: итог считается с учётом последнего решения.

## Итог

Итог = 100 × Σ(вес × доля) / Σ(вес применимых критериев), доля: да 1, нет 0, шкала — ступень / максимум. N/A и `pending` исключаются, флаги в сумму не входят. Округление только итога, до двух знаков, половина вверх. Векторы проверки: `tests/fixtures/scoring_vectors.json` (77,69 и 82,94 из прототипа).

| `GET /api/config` | — | `{llm_mode, llm_provider, providers, llm_base_url, llm_model, llm_profile, profiles, has_llm_key, data_where, anonymize, verifier, evaluator, has_jev_key, allow_real_data, features}` — режим оценки без ключей; `features` — ключи разделов, которые сервер умеет (`alerts`, `employees`, `audit`, `reports`, `usage`, `telemetry`, `docs`, `sources`, `batches`, `routing`, `automation`; ключ есть, если зарегистрирован его маршрут); провайдеры — раздел «Провайдеры моделей», `evaluator` — «Режим „только Jev“» |
| `PUT /api/config` | `{llm_provider, verifier, evaluator, anonymize, jev_api_key, allow_real_data}` (раздел «Провайдеры моделей») | то же, что `GET /api/config`, после применения |
| `GET /api/employees` | — | `[{id, name, role, team, active}]` по имени; раздел «Сотрудники и журнал действий» |
| `PUT /api/employees/{id}` | `{name, role: "operator" \| "qa" \| "reviewer" \| "manager" \| "admin", team, active}` | сотрудник после записи: создан или изменён; пустое имя или другая роль — 422 |
| `POST /api/employees/import` | CSV `id;name;role;team`, UTF-8 (BOM можно), первая строка `id;…` — заголовок | `{added, updated}`; ошибка в строке — 422 «Строка N: …», ничего не сохранено |
| `GET /api/me` | — | `{id, name, role}` сотрудника из `X-CQA-User`; без входа `{id: null, name: "без входа", role: ""}` |
| `GET /api/audit?actor=&action=&since=&limit=&format=json\|csv` | — | журнал новыми первыми: `[{id, at, actor_id, actor_name, role, action, target_type, target_id, details}]`; без `limit` json — 500 последних, csv — весь отбор (`attachment; filename="cqa-audit.csv"`) |
| `GET /api/overview` | — | обзор работы: `{at, employees, teams, unattributed, workload}` |

Ссылки организаторов на записи подписаны и живут около часа, поэтому в браузер они не уходят: интерфейс ходит только в `/audio` и `/player`. Сервер хранит `audio_url` в колонке таблицы `dialogs` и не отдаёт её ни в одном ответе. Если ссылку получить не удалось, `/audio` отвечает 502.

`POST /api/datasets` и `/upload`: битые записи входят в `skipped`, их идентификаторы и причины пишутся в журнал сервера.

`PUT /api/source`: ссылка API организаторов из интерфейса. Нужен `https://`, иначе 422; сбой API организаторов — 502, прежняя ссылка остаётся. Сервер хранит ссылку в базе, она важнее `CQA_ORG_API_URL`, в том числе для `POST /api/datasets`, и не уходит ни в один ответ. Сервер забирает сохранённый `group_id` при старте и раз в 5 минут, новые диалоги добавляются, дубли по `id` пропускаются, оценка сама не запускается.

`source` в `GET /api/state`: `null`, пока ссылки нет, иначе `{"group_id": "DEV", "synced_at": "<ISO>", "added": 0, "skipped": 65, "error": null | "<текст>"}`; до первого прохода после старта есть только `group_id`.

Ручной ответ — новый результат пары: итог берёт последний результат, запуск оценки пару с результатом пропускает, прежний ответ модели остаётся в базе. Для флага `a` — `{"<k>": true | false}` по каждому вопросу, для остальных — значение из `allowed_answers`, иначе 422. Апелляция на рассмотрении или решение по паре текущего смысла — 409: решение важнее ответа.

`PUT /api/config` применяется без перезапуска: сервер пересобирает оценщик, `mode` в состоянии меняется сразу; во время запуска — 409. Значения хранятся в базе поверх `.env` и переживают перезапуск. Пустой `jev_api_key` или `key` провайдера оставляет сохранённый ключ; ключи не уходят ни в один ответ. Ошибка конфигурации (нет ключа для `live`, неизвестный профиль, Jev без ключа, адрес не `http(s)://`) — 422, режим не меняется. Интерфейс открывает окно режима по клику на плашку `mode`.

`mode` описывает режим данных для плашки в интерфейсе: `{"where": "kz" | "local" | "external", "anonymized": true, "model": "qwen3-6", "verifier": "jev" | "self" | null}`.

## Провайдеры моделей (llm-evaluation)

Несколько OpenAI-совместимых моделей, у каждой свой ключ. Раздел уточняет `GET /api/config` и `PUT /api/config` из таблицы HTTP API: `PUT /api/config` выбирает провайдера, адрес и ключ модели задаёт `PUT /api/providers/{id}`.

Provider: `{"id": "deepseek", "label": "DeepSeek", "base_url": "https://api.deepseek.com", "model": "deepseek-chat", "profile": "plain" | "deepseek", "where": "kz" | "local" | "external", "has_key": true}`. `id` — строчная латиница, цифры и дефис, до 32 знаков. Провайдер `env` есть всегда: он собран из `CQA_LLM_*` и `CQA_DATA_WHERE` (и полей, сохранённых прежней формой режима) и меняется только в `.env`.

| Метод и путь | Тело | Ответ |
| --- | --- | --- |
| `GET /api/config` | — | поля из таблицы HTTP API и `llm_provider` (код основной модели), `providers: [Provider]`; `llm_base_url`, `llm_model`, `llm_profile`, `has_llm_key`, `data_where` описывают основную модель |
| `PUT /api/config` | `{llm_provider, verifier: "jev" \| код провайдера \| null, evaluator: "llm" \| "jev", anonymize, jev_api_key, allow_real_data}` | то же, что `GET /api/config`, после применения |
| `PUT /api/providers/{id}` | `{label, base_url, model, profile, where, key}` | то же, что `GET /api/config`: провайдер создан или изменён |
| `DELETE /api/providers/{id}` | — | то же, что `GET /api/config` |
| `POST /api/providers/{id}/check` | — | `{ok: true \| false, ms, error: null \| "<текст>"}` |

Ключ только записывается: ни в ответах, ни в журнале его нет, есть `has_key`; пустой `key` при изменении оставляет сохранённый. Список провайдеров хранится в базе и заменяет `CQA_PROVIDERS` из `.env`.

Провайдер `openrouter-jev` (Jev Router через OpenRouter) есть всегда, вторым после `env`: `{"label": "OpenRouter — Jev Router", "base_url": "https://openrouter.ai/api/v1", "model": "typesafe/jev-router", "profile": "plain", "where": "external"}`, ключ — `CQA_OPENROUTER_API_KEY` или `PUT`. `PUT /api/providers/openrouter-jev` меняет только `model` и `key`, остальные поля тела игнорирует; `DELETE` не удаляет, а возвращает его к умолчанию (409 — как у других, если он выбран). Если провайдер возвращает `usage.cost` (OpenRouter), `cost` — эта цена, а не цена за токены.

Основная модель — провайдер `llm_provider`: его `where` становится `mode.where`, `model` — `mode.model`. `verifier`: `"jev"`, код провайдера (те же вопросы по критериям уходят модели этого провайдера, её ответ — в `alt`) или `null`; `mode.verifier` повторяет его, поэтому в `mode` бывает и код провайдера.

Ошибки: неизвестный провайдер в `llm_provider` или `verifier`, нет ключа для `live` — 422, режим не меняется. Неверный `id`, адрес не `http(s)://`, неизвестный профиль, `PUT /api/providers/env` — 422. `DELETE` основной модели, второго мнения или `env` — 409, неизвестный `id` — 404. Любое изменение во время запуска — 409, как у `PUT /api/config`.

`POST /api/providers/{id}/check`: один запрос `max_tokens: 1` с синтетическим текстом «Ответь одним словом: да», без повторов, таймаут 20 секунд, реальные данные не уходят; запрос идёт в сеть и в режиме `replay`. Ошибка провайдера — `ok: false` с текстом, а не код HTTP; неизвестный `id` — 404.

## Режим «только Jev» (llm-evaluation, jev-only)

- `GET /api/config` отдаёт, а `PUT /api/config` принимает поле `evaluator`: `"llm"` (по умолчанию) или `"jev"`; в `.env` — `CQA_EVALUATOR`. Другое значение — 422.
- `evaluator: "jev"`: все критерии диалога отвечает Jev одним запросом (choice на критерий, noul на подвопрос флага). Языковая модель и второе мнение не вызываются, адрес и ключ модели не нужны. Без ключа Jev вне `replay` — 422 «Нет ключа Jev…», режим не меняется. Канал (`na` без вопроса) и обезличивание — как у языковой модели.
- `mode` в этом режиме: `model` — имя модели Jev (`"jev-latest"`), `verifier: null`.
- `CriterionResult` в этом режиме: `a` — ответ Jev; `why` — «Ответ Jev с вероятностью 0,93; модель не пишет обоснований» (у флага — наименьшая вероятность по вопросам), других причин нет; `ev: []`, без `quote`, `seg`, `tag`, `better`, `alt`; `model: "jev-latest"`; `calls: 1` у первого ответа диалога и `0` у остальных, `cost` — цена запроса поровну между ответами, `ms` — время запроса.
- Вероятность ниже 0,6 или её нет — `evFail: true`, ответ в «Нужна проверка»; карточка и очередь пишут «Jev не уверен в ответе». Флаг возвращается всегда: подвопрос без ответа — «не найдено» и `evFail: true`. Нет ответа по критерию — записи нет, критерий ждёт оценки. Сбой запроса — сбой всего диалога.
- `Dialog.cost` в этом режиме: `calls: 1`, `verifier_calls: 0`. `make eval` с `CQA_EVALUATOR=jev` оценивает эталон только Jev.

## Интонация звонка (dialog-ingest, prosody)

| Метод и путь | Тело | Ответ |
| --- | --- | --- |
| `GET /api/dialogs/{id}/prosody` | — | `{lines, speakers, summary, talk}` — интонация звонка по звуку записи; 404 — чат, неизвестный id или звонок без записи; 502 — запись не получена |

```json
{"lines": [{"n": 12, "f0": 214, "range_st": 6.3, "db": 71.2, "wps": 2.6, "pause": 0.8, "flags": ["raised"]}],
 "speakers": {"client": {"f0": 180.0, "db": 66.0, "wps": 2.5, "lines": 30},
              "operator": {"f0": 110.0, "db": 65.0, "wps": 2.3, "lines": 28}},
 "summary": ["Клиент повысил тон в репликах 12–14", "Пауза 9 с перед ответом оператора (реплика 20)"]}
```

- `lines`: реплики клиента и оператора с `s`, в порядке расшифровки. `f0` — медиана тона, Гц; `range_st` — размах тона p10–p90, полутоны; `db` — средняя интенсивность речи, дБ по шкале записи; `wps` — слов в секунду речи; `pause` — тишина перед репликой после предыдущей реплики клиента или оператора, с. `null` — нет речи, тона или предыдущей реплики.
- Запись моно, говорящие различаются только по расшифровке: реплика кончается на метке `s + utterance_s(text)`, её речь — громкие кадры между концом предыдущей реплики и этой меткой.
- `speakers`: обычная манера говорящего — медианы `f0`, `db`, `wps` по его репликам с `seg` `conv` или без `seg`; `lines` — их число.
- `flags` ставятся только репликам `conv` (удержание и разговор с коллегой — `internal` — не оцениваются). Относительно манеры того же говорящего, если у него не меньше 3 реплик и реплика звучит не меньше 1,5 с: `raised` — тон на 3 полутона выше или на 6 дБ громче; `fast` — темп не меньше 1,5 обычного и 3,5 слова в секунду. Абсолютные: `monotone` — размах меньше 2 полутонов на реплике от 4 с; `long_pause` — ответ оператора клиенту после 5 с тишины и больше; `overlap` — реплика началась на 1 с и больше раньше конца чужой и позже её начала. Пороги эвристические, константы в `src/cqa/domain/prosody.py`.
- `summary`: фразы по-русски по флагам; подряд идущие реплики одного говорящего — диапазоном.
- `talk`: статистика разговора по тем же отрезкам речи (раздел «Статистика разговора»). Разбор, сохранённый без `talk`, отдаётся как есть; `/talkstats` считает его заново один раз.
- Считается при первом запросе (свежая ссылка, скачивание в память, ffmpeg и Praat на сервере) и хранится в таблице `prosody`; 502 не сохраняется, следующий запрос пробует снова. Запись никуда не отправляется; в модель уходит только сводка (см. «Интонация в оценке звонка»).
- Интерфейс: карточка звонка запрашивает интонацию при открытии и показывает панель «Интонация» со сводкой и значки у реплик: `↑ тон`, `монотонно`, `быстро`, `пауза N с`, `перебивание`. Чат не запрашивает; 404 — панели нет; 502 — приглушённая строка «Интонация недоступна».

### Интонация в оценке звонка (llm-evaluation)

- Оценщик (`LlmEvaluator`, `JevEvaluator`, второе мнение) у звонка берёт разбор `dialog_prosody` (из таблицы `prosody` или считает) и добавляет блок `sound_block(summary)` после `</dialog>` (Jev и второе мнение — следом за репликами в тексте диалога): строка «Анализ звука записи (автоматически, по тону и громкости; распознавание речи не проверялось):», строки `summary` с «- » (пустая сводка — «- отклонений тона, громкости, темпа и пауз не найдено»), правило: тон, паузы и темп — по этим строкам, сверх них о звуке ничего, дикции и разборчивости по ним не оценить.
- Чат, звонок без записи, 404/502, нет ffmpeg или любая ошибка разбора — блока нет, запрос байт в байт прежний; системный промпт не меняется. Запрет реальных звонков (`CQA_ALLOW_REAL_DATA`) проверяется до разбора; в блоке только роли и номера реплик, без текста и имён.
- Отпечаток (`fingerprint`) звук не учитывает: появление интонации готовые ответы не пересчитывает, она входит в следующие оценки звонка. `make eval` идёт без интонации.

## Статистика разговора (dialog-ingest, talkstats)

| Метод и путь | Тело | Ответ |
| --- | --- | --- |
| `GET /api/dialogs/{id}/talkstats` | — | `{ch, rule, n, note, metrics: [{key, label, unit, value, median, lo, hi, out_of_norm}]}`; 404 — неизвестный id, звонок без записи, чат без ответов оператора с метками; 502 — запись звонка не получена |
| `GET /api/talkstats/norms` | — | `{rule, call: Norms, chat: Norms, operators: {"<Dialog.operator>": {call: Norms, chat: Norms}}}`, Norms — `{n, note, metrics: [{key, label, unit, n, median, q1, q3, iqr, lo, hi}]}` |

```json
{"ch": "call", "n": 12, "note": null,
 "rule": "Вне нормы — значение за границами Тьюки [Q1 − 1,5·IQR; Q3 + 1,5·IQR] по диалогам команды того же канала; меньше 5 диалогов — нормы нет",
 "metrics": [{"key": "monologue_s", "label": "Самый долгий монолог оператора", "unit": "с",
              "value": 48.2, "median": 21.0, "lo": 2.5, "hi": 41.5, "out_of_norm": true}]}
```

- Звонок — из разбора `/prosody` (`talk`), звук заново не разбирается. Считаются только реплики `conv` (и без `seg`); удержание и разговор с коллегой делят звонок на участки, их время не входит ни в речь, ни в тишину.
- Метрики звонка по порядку: `operator_share` — доля времени речи оператора от речи оператора и клиента, %; `monologue_s` — самый долгий монолог оператора: от начала первой до конца последней его реплики подряд, без реплик клиента между ними, с; `pause_median_s`, `pause_max_s` — тишина перед ответом оператора на реплику клиента, с; `interrupt_operator`, `interrupt_client` — сколько раз сторона перебила другую (флаг `overlap` разбора); `silence_share` — доля тишины на участках разговора, %; `wps_operator`, `wps_client` — слов в секунду речи стороны.
- Метрики чата: `reply_median_s`, `reply_max_s` — от первого неотвеченного сообщения клиента до ответа оператора по меткам `t`, только `conv` (и без `seg`): ожидание в очереди к боту в норму оператора не входит.
- Норма — по всем диалогам канала в базе: звонки — с сохранённым разбором с `talk`, чаты — с хотя бы одним ответом. `median` при любом `n`; `q1`, `q3` — квартили (`statistics.quantiles`, `inclusive`), `lo = q1 − 1,5·iqr`, `hi = q3 + 1,5·iqr`. Меньше 5 значений метрики — `lo`, `hi`, квартили `null`; меньше 5 диалогов канала — `note: "недостаточно данных: 3 из 5 диалогов"`.
- `operators`: те же Norms по диалогам каждого сотрудника (`Dialog.operator`, без сотрудника — только в общей норме); главное в них — `median`, отметки `out_of_norm` по ним не ставятся.
- `out_of_norm`: `true` — значение вне `[lo; hi]`, `false` — внутри, `null` — нет значения или нормы. `value: null` — метрику не посчитать (нет ответов оператора, нет речи стороны).
- Только время: длительности речи, паузы, наложения и темп; интонационные признаки — в `/prosody`, содержание реплик не читается.
- Интерфейс: блок «Статистика разговора» в карточке — строки `label`, `value` `unit`, рядом медиана команды; точка у `out_of_norm: true`; `note` — приглушённой строкой; 404 — блока нет.

## Отчёт для руководства (eval-and-delivery)

JSON: `{at, filters: {lang, ch, operator}, summary: {dialogs, scored, avg_total, risk: {dialogs, share, kinds: [{k, label, n}]}, no_next_step: {dialogs, share}, needs_review, open_appeals, cost: {dialogs, avg_usd, avg_s}}, criteria: [{id, name, n, na, share}], reasons: [{tag, dialogs, owner, criteria}], channels, langs: [{key, label, n, avg}], operators: {attention: [OperatorRow], strengths: [OperatorRow]}, findings: [строка]}`. Ответы с учётом последнего решения, итог как в «Итог», доли от оценённых диалогов: `no_next_step` — ступень ниже верхней у `signal: "resolution"`, `needs_review` — не проверенные диалоги с расхождением или `evFail` без решения. `criteria` — средняя доля баллов без N/A, худшие первыми; `reasons` — топ-10 `tag` сниженных ответов; `findings` — 3–5 выводов по-русски из чисел, без модели. `html` — самодостаточная страница A4 для печати, данные экранированы; `md` — для вики и почты; без оценённых диалогов — «Нет оценённых диалогов».

## По сотрудникам (eval-and-delivery)

OperatorRow: `{operator, dialogs, n, avg_total, sd, ci95: [lo, hi] | null, ranked, reason: null | "<почему не ранжирован>", gross_errors, needs_review, appeals_open, weakest: [{cid, name, share}], trend: [{day, avg_total, dialogs}]}`.

- Считается из того же текущего состояния, что `GET /api/state` и отчёт: ответы с учётом последнего решения, итог как в «Итог». Диалоги без `operator` — группа «Не указан».
- `dialogs` — все диалоги сотрудника, `n` — оценённые (есть итог), `avg_total` — их средний итог (`null` при `n = 0`); `sd` — выборочное стандартное отклонение итога (делитель `n − 1`); `ci95` — 95 % доверительный интервал среднего по Стьюденту: `avg ± t(0,975; n − 1) · sd / √n`, обрезан до 0–100; при `n < 2` `sd` и `ci95` — `null`. Тексты определений сервер отдаёт в `definitions`, интерфейс показывает их в подсказках.
- `ranked: true` только при `n ≥ min_n` (`MIN_SCORED = 5` в `src/cqa/domain/report.py`: при `n = 4` одна оценка сдвигает среднее на четверть шкалы, а интервал — ±1,6 стандартного отклонения) и известном сотруднике; иначе `reason`: «недостаточно данных (n=3, нужно ≥5)» или «сотрудник не указан». Порядок `operators`: ранжированные по возрастанию `avg_total` (кому нужна помощь — выше), затем остальные по убыванию `n`.
- `gross_errors`, `needs_review`, `appeals_open` — как `risk.dialogs`, `needs_review`, `open_appeals` отчёта по его диалогам. `weakest` — до трёх критериев с наименьшей средней долей баллов ниже 1, худший первым. `trend` — по дням `ДД.ММ` из `at` в порядке календаря: средний итог и число оценённых диалогов дня (у чата `at` — время загрузки набора).
- Раздел отчёта «По сотрудникам» — только ранжированные, и только если их не меньше двух: `attention` («требуют внимания», до 5 с меньшим средним итогом) и `strengths` («сильные стороны», до 3 с большим); списки не пересекаются, при малом числе сотрудников в `strengths` не больше половины. В таблицах — n, средний итог и 95 % интервал. Это не рейтинг: формулировок «лучший», «худший», «место» в интерфейсе и отчётах нет.

## Рекомендации (eval-and-delivery)

Чистые функции `src/cqa/domain/recommend.py`, без модели и без весовых сумм: явные правила над ответами с учётом последнего решения и формулой «Итог». Сотрудник — `Dialog.operator`, продукт — `Dialog.product`; пока поля продукта нет, разрез по нему пуст.

Общее в каждом ответе: `{for, params: [{name, value, why}], insufficient: [{subject, n, need, text}]}`. Пункт рекомендации: `{title, why, basis: {rule, numbers, dialogs: [{id, cid?, lines}]}, …}` — `why` — «почему» одним предложением с числами, `basis.rule` — правило словами, `numbers` — числа с размерами выборок, `dialogs` — до 5 диалогов-доказательств с номерами реплик (`lines` из `ev`). Правило сработало бы, но выборка меньше порога — вместо пункта строка `insufficient`: `text` «недостаточно данных (n=3, нужно ≥5)». Пороги — `params`: `MIN_N` 5 (при n < 5 один диалог сдвигает долю на 20 п. п.), `MIN_UNIFORM` 20, `UNIFORM_SHARE` 0,95, `DISPUTE_SHARE` 0,2, `NA_SHARE` 0,5, `WEIGHT_RATIO` 2, `ATTENTION_GAP` 10, `TREND_DROP` 5, `LOW_SD` 1, `REPEAT` 2; обоснование каждого — в `why`.

- `for=operator&id=<имя>`: `{operator, summary: {dialogs, scored, avg_total, team_dialogs, team_avg_total}, items, strength}`. `items` — до 3 навыков `{kind: "skill", cid, name, better: [{id, text}], peers: [{id, operator, lines, quote, match}]}`: критерии с наибольшим отставанием средней доли сотрудника от доли коллег (другие сотрудники), при ≥ `MIN_N` оценок у обеих сторон; `numbers {share, team_share, gap, n, team_n, lost}`; `basis.dialogs` — 1–2 своих диалога с худшей долей (`lines`, `seg`, `quote`, `tag`, `a`); `better` — «как сказать лучше» из своих результатов; `peers` — диалоги коллег с максимумом по критерию, сначала тот же продукт и язык, затем продукт, затем язык, только сохранённая `quote`. `strength` — лучший свой критерий не ниже коллег или `null`.
- `for=qa`: `{rules: [{k, n, text}], items: [{id, rule, total, operator, reasons: [{k, text, cid, lines}]}]}` — очередь «Проверить сначала» по упорядоченному списку правил: 1 `gross` грубое нарушение, 2 `disagree` второе мнение разошлось, 3 `evidence` основание не найдено, 4 `jev` Jev не уверен (каждое — без решения по паре), 5 `low` итог ниже среднего набора больше чем на `LOW_SD` σ, 6 `tone` клиент повысил тон (сохранённая интонация, реплики клиента с `raised`), 7 `new_operator` у сотрудника меньше `MIN_N` диалогов, 8 `product_trend` диалог поздней половины продукта со снижением итога. Порядок: первое сработавшее правило, затем больше правил, ниже итог (без итога — первым), id. Проверенные диалоги не входят.
- `for=manager`: `{actions, operators, trends}`. `actions` `{kind: "reason", owner, tag, product, uplift}` — сниженные ответы одной причины `tag` в одном продукте, хотя бы в `REPEAT` диалогах; действие по `owners` («Обновить инструкцию», «Изменить процесс сервиса», «Доработать продукт», «Назначить ответственного»); `uplift` = Σ(итог диалога с этими критериями на максимуме − итог) / число оценённых диалогов; по убыванию `uplift`; `numbers {dialogs, scored, avg_total, uplift, criteria, channels}`. `operators` — грубое нарушение (любое n) или средний итог ниже среднего набора на ≥ `ATTENTION_GAP` при ≥ `MIN_N` диалогах. `trends {dim: product|ch|lang, key, label}` — диалоги группы по `at` пополам, поздняя половина ниже ранней на ≥ `TREND_DROP` при ≥ `MIN_N` в каждой; `numbers {earlier_n, later_n, earlier_avg, later_avg, drop}`.
- `for=checklist`: `items [{kind, cid, name}]`, порядок `ambiguous`, `weight`, `na`, `uniform`, внутри — порядок чек-листа. `uniform` — один ответ у ≥ 95 % оценок при n ≥ 20 (флаги не проверяются); `ambiguous` — доля ≥ 20 % хотя бы по одной мере при её n ≥ `MIN_N`: решения, изменившие ответ (`decided`/`changed`), расхождение второго мнения (`second`/`disagree`), ручные ответы (`answers`/`manual`); `na` — N/A в ≥ 50 % оценок; `weight` — доля потерь ≥ 2 × доля веса, потеря критерия = 100 × вес × (1 − доля) / сумма весов применимых, `suggested_w` = доля потерь × сумма весов.
## Аналитика (eval-and-delivery)

Из того же состояния, что `GET /api/state`: ответы с учётом последнего решения, итог как в «Итог», числа совпадают с отчётом для руководства. Фильтры: `lang` без учёта регистра, `ch`, `operator` и `product` — точное совпадение поля диалога, `Не указан` — диалоги без него, `since`/`until` — дата диалога включительно; дата — день из `at`, года в `at` нет: текущий год, дата позже сегодняшней — прошлого года. Апелляции — только по выбранным диалогам.

Общая часть каждого ответа: `{name, filters: {lang, ch, operator, product, since, until}, by, n, min_n: 5, definitions: {<метрика>: "<формула по-русски>"}}`. `n` — оценённые диалоги выборки. У каждой точки и ячейки есть своё `n` и `low_n: n < min_n` (выводы по ней не делаются). Счётчик — `{k, n, share: k/n, low_n}`, ячейка доли — `{n, share, low_n}`; `share` — 4 знака, итоги — 2.

- `trend?by=day|week` (без `by` — `day`): `criteria: [{id, name}]`, `points: [{period, start (только week), n, low_n, avg_total, gross, no_next_step, needs_review, criteria: {<id>: ячейка}}]`; `period` — `ГГГГ-ММ-ДД` или ISO-неделя `ГГГГ-Wнн`, по возрастанию.
- `heatmap?by=operator|product|lang|ch` (без `by` — `operator`): `columns: [{id, name, n, share}]`, `rows: [{key, label, n, low_n, avg_total, cells: {<id>: ячейка}}]`, больше диалогов — выше; без значения поля — `key: null`, `label: "Не указан"`.
- `drivers`: `base` — средний итог, `drivers: [{id, name, n, at_max: {n, avg_total, gross}, below_max: {…}, gap, low_n, r, lowest: счётчик, uplift, avg_total_if_max, what_if}]` по убыванию `uplift`, затем `gap`. `gap` — разница средних итогов при доле 1 и ниже 1; `r` — корреляция Пирсона доли с итогом (`statistics.correlation`, null при n < 2 или постоянной величине); `lowest` — диалоги, где доля критерия минимальна и меньше 1; `uplift` — прирост среднего итога, если ответ критерия поднять до верхнего везде, где он применим (формула «Итог»); `what_if` — фраза по-русски.
- `distribution`: `totals: [{lo, hi, n, share}]` — корзины по 10, последняя `[90; 100]`; `criteria: [{id, name, type, n, answers: [{a, n, share}]}]` — ответы в порядке допустимых, у флага `[{a: k, label, n, share}]`.
- `crosstab`: `cells: [{ch, lang, product, n, low_n, avg_total, gross}]`, больше диалогов — выше.
- `appeals`: `summary: {filed, reviews, pending, closed, decided, changed, confirmed, changed_share, low_n, median_hours, timed}`, `criteria: [{id, name, filed, reviews, decided, changed, confirmed, changed_share, low_n}]` по убыванию `changed_share`, `reviewers: [{reviewer, decided, changed, changed_share, low_n, median_hours, timed}]`. `median_hours` — медиана часов от `at` до `decidedAt` решённых апелляций (`kind: "appeal"`).
- `model?by=day|week`: по сырым результатам, без решений: `criteria: [{id, name, results, second_opinion, ev_fail, jev_unsure, manual}]` — счётчики: `alt = a` среди результатов с `alt`; `evFail` основной модели; `evFail` у результатов Jev; ручные ответы. `cost: [{period, n, avg_usd, avg_s, low_n}]` — по диалогам с `cost`.
## Отчёты по замерам (eval-and-delivery, reports-hub)

Все отчёты, кроме файлов результатов, отдаются в одних форматах: `json` — данные как есть, для аналитики; `csv` — UTF-8 с BOM и `;`, таблицы блоками через пустую строку, ячейка с `= + - @` в начале — с апострофом; `md` — для вики и почты; `html` — самодостаточная страница A4 в стиле памятки чек-листа. Без `format` — `html`. `html` — `Content-Disposition: inline`, `csv` и `md` — `attachment; filename="<имя>.<формат>"`.

`GET /api/reports`: `[{"id": "quality", "title": "Качество оценки", "description": "…", "formats": ["html", "json", "md", "csv"], "href_template": "/api/quality/{id}?format={format}", "items": "/api/quality"}]`. В `href_template` интерфейс подставляет `{format}` из `formats`, `{id}` — `id` элемента списка `items`, `{from}` — версию чек-листа. Отчёт попадает в каталог, только если его путь есть в приложении. `id`: `executive`, `quality`, `run` (`items: "/api/runs"`), `scores`, `operators`, `checklist`, `checklist-diff`; `results-dev` и `results-prod` — только если файл есть.

`GET /api/quality`: прогоны из `CQA_EVAL_REPORTS_DIR` (`eval/reports/<YYYYMMDDTHHMMSSZ>.json`, пишет `make eval`); `created` — время из имени файла, ISO UTC; `passed` — пустой `problems`. Файлы `holdout-*`, битые и чужого формата пропускаются.

`GET /api/quality/{id}`: `json` — тело файла `make eval` (поля `Report`, `cost_per_dialog`, `calls_per_dialog`, `problems`) и `{id, created, thresholds: [{name, label, limit, upper, value, ok}]}` — каждый порог `eval/thresholds.yaml` против значения прогона: `upper` — порог сверху, `ok: null` — значения нет (у `baseline_drop_max_pts` всегда, регресс к лучшему прогону — в `problems`). `csv`, `md`, `html` — сводка, совпадение по языкам и критериям, полнота грубых ошибок по видам и языкам и ложные флаги, пропущенные грубые ошибки, N/A, цена и время, пороги, замечания прогона, расхождения (диалог, критерий, эталон, ответ модели). Обоснования и цитаты модели (`why`, `quote`) — только в `json`: печатные отчёты не несут текста, производного от диалогов. Отчёты `make eval` в git не попадают.

`GET /api/runs/{id}/report`: `json` — `{id, total, done, cost, calls, errors, status, started, finished, started_at, finished_at, progress, models: [строка], checklist_versions: [число], criteria: [{cid, name, n, answers: {"yes": 5, "no": 2, "na": 1, "3": 4, "<k>+<k>": 1, "none": 3}}]}`; `answers` — ответы запуска по значению (флаг — отмеченные подвопросы через `+`, `none` — без нарушений). Ответы запуска — результаты, записанные между `started` и `finished` (у идущего — до сейчас), включая ручные.

## Доступ по токену (eval-and-delivery)

Пустой `CQA_ACCESS_TOKEN` — всё открыто, как раньше. Заданный: `GET /login?token=<токен>` — 302 на `/` и cookie `cqa_access` (HttpOnly, SameSite=Lax, path `/`), неверный токен — 401 со страницей входа без cookie. Без верной cookie `/api/*` — 401 `{"detail": "Нужен вход по ссылке с токеном"}`, остальные пути — 401, самодостаточная страница «Доступ по ссылке с токеном» без данных; `GET /api/health` открыт всегда. Сравнение — `hmac.compare_digest`, значение `token=` в журнале uvicorn заменено на `***`.

## Источники диалогов (dialog-ingest, sources)

Диалоги приходят из нескольких сервисов; у каждого диалога есть происхождение. `Dialog` получает поля `source_id` (id источника) и `external_id` (id записи в источнике); поле записи `operator` становится `Dialog.operator`, `product` (или `product_default` источника) виден в предпросмотре — тему диалога определяет раздел «Темы обращений»; дубли — по `(source_id, external_id)`. Диалоги организаторов и файла сохраняют `id` = `conversation_id`, у `http_json` и `webhook` `id` = `<source_id>-<external_id>`, название — «Чат <external_id>» / «Звонок <external_id>». `GET /api/state` получает `sources: [{id, name, kind, service}]` (без архивных) для фильтра и плашки источника.

Source: `{"id": "src1", "name": "Чат-платформа", "kind": "org_api" | "http_json" | "webhook" | "file" | "paste" | "api", "service": "ChatDesk", "channel_default": "chat" | "call" | null, "product_default": "Карты" | null, "config": {…}, "has_secret": true, "enabled": true, "schedule_min": 5, "created": "<ISO>", "archived": false, "ingest_path": "/api/sources/src1/ingest" | null}`. Встроенные: `org` (API организаторов, по умолчанию выключен, расписание 5 мин; прежняя ссылка `PUT /api/source` переносится в него), `file` (`POST /api/datasets/upload`), `paste` (`POST /api/dialogs/text`), `api` (интеграционный API). Встроенные не удаляются; у `file`, `paste`, `api` меняются только `name`, `service`, `channel_default`, `product_default`.

`config` (не секрет) по виду:
- `org_api`: `{"group_id": "DEV"}`; секрет — подписанная ссылка `https://…`. Включить без ссылки — 422.
- `http_json`: `{"url": "https://…", "method": "GET" | "POST", "auth_header": "Authorization" | "", "records_path": "data.items", "mapping": Mapping}`; секрет — значение заголовка. Логин, пароль или параметр вроде `token`, `key`, `signature` в адресе — 422 (адрес виден в интерфейсе).
- `webhook`: `{"auth": "bearer" | "hmac", "records_path": "", "mapping": Mapping}`; секрет — токен, его выдаёт сервер.

Mapping: пути (`agent.name`, `data.items.0`) к полям записи: обязательные `conversation_id`, `transcript` (список реплик), `speaker`, `text` (внутри реплики); необязательные `channel`, `language`, `timestamp` (внутри реплики), `audio_url`, `operator`, `product`, а также `speakers: {"<значение>": "client" | "operator" | "bot" | "system"}`. Роли и каналы понимаются по синонимам (`agent`, `customer`, `user`, `chat`, `call`, `voice`…); нет канала — `channel_default`; нет языка — по тексту; нет времени — `MM:SS` по номеру реплики.

Автосинхронизация: включённые `org_api` и `http_json` с `schedule_min > 0`, проверка раз в 30 с.

SourceStats: `{id, name, kind, enabled, archived, dialogs, scored, avg_total, gross_share, running: SourceSync | null, last_sync: SourceSync | null, syncs, error_rate, newest_at, freshness_s, health: "ok" | "warning" | "error", basis}`. Итог и грубые ошибки — с учётом решений, как в отчёте; `error_rate` — доля `error` среди последних 10; `freshness_s` — возраст самого нового диалога. `health` — первое сработавшее правило, `basis` — его текст: выключен — warning «источник выключен»; последняя синхронизация `error` — error «последняя синхронизация с ошибкой: <первая ошибка>»; `error_rate > 0,2` — warning «N% синхронизаций с ошибкой (последние 10)»; `partial` — warning «последняя синхронизация с пропусками: N записей не разобраны»; `file`, `paste`, `api` — ok «загрузка вручную» / «ошибок нет»; pull без синхронизаций — warning «ещё не синхронизировался»; нет данных — warning «данные ещё не поступали»; новый диалог старше 24 ч — warning «нет новых данных 24 ч»; иначе ok.

`http_json` ходит только в публичный интернет: адрес, который резолвится в частную сеть, loopback, link-local (169.254.169.254) и другие служебные диапазоны, — `ok: false` / `error` «адрес … во внутренней сети», перенаправления не выполняются. `CQA_ALLOW_PRIVATE_SOURCES=1` снимает запрет (источник в своей сети, `make demo`). Отчёт для руководства: `sources: [{key, label, n, avg}]` («По источникам»), фильтр `source=<id>`, `filters.source`.

## Сотрудники и журнал действий (eval-and-delivery)

Пароля нет: в продукте личность даёт SSO / Dynamics 365 (Entra ID), заголовок ставит шлюз или встраивание, сервер ему доверяет. ## Пакетная обработка (eval-and-delivery)

Большие объёмы оцениваются заданиями: задание делится на батчи, одна очередь в процессе отдаёт батчи `Runner` по одному. Каждый батч — обычный запуск (`POST /api/runs` с его диалогами), поэтому правило одного активного запуска сохраняется: пока идёт запуск вне очереди, очередь ждёт его конца. Следующий батч берётся у задания с высшим приоритетом (`high` → `normal` → `low`), внутри приоритета — по порядку создания; новое задание `high` обгоняет начатое `normal` на границе батча.

| Метод и путь | Тело | Ответ |
| --- | --- | --- |
| `POST /api/batches` | `{"dialogs": [..]}` или `{"filter": {source_id?, ch?, lang?, product?, since?: "YYYY-MM-DD", unscored_only: true}}`, `batch_size: 20` (1..200), `priority: "high" \| "normal" \| "low"` (`normal`), `force: false` | Job |
| `GET /api/batches` | — | `{jobs: [Job без batches и failed], rate_limit}`, новые первыми |
| `GET /api/batches/{id}` | — | Job |
| `POST /api/batches/{id}/pause \| resume \| cancel \| retry` | — | Job после действия |

Job: `{id, status: "queued" | "running" | "paused" | "done" | "cancelled" | "failed", priority, batch_size, force, note, created, total, done, errors, pending, cost, throughput_per_min, eta_s, eta_basis, batches: [{no, n, done, errors, started, finished, cost, run_id}], failed: [{dialog, error}], rate_limit: {rpm, parallel}}`. Счётчики — в диалогах; `started`, `finished` — ISO UTC, `cost` — USD из запусков батча (с повторами), `run_id` — последний запуск батча, его ход — `GET /api/runs/{run_id}`.

- Ровно один из `dialogs` и `filter`, иначе 422; неизвестный диалог — 404; пустой выбор — 422. Фильтр: равенство полей диалога (`source_id`, `ch`, `lang`, `product`; поля, которого у диалога нет, ничего не находит), `since` — дата `at` не раньше (в `at` нет года: сравнение в пределах года), `unscored_only` — только диалоги с парами без текущего результата. Неизвестное поле фильтра — 422. `force: true` — 422, пока `Runner` не умеет повторную проверку: батч оценивает только пары без текущего результата.
- `pause` (из `queued`, `running`) и `cancel` (из `queued`, `running`, `paused`) не прерывают батч в работе: он дорабатывает (не больше `batch_size` диалогов), следующий не начинается. `resume` — из `paused` в `queued`. `retry` — диалоги с ошибкой снова в очередь, задание `done`/`failed` → `queued`, `paused` остаётся на паузе; без ошибок или у `cancelled` — 409. Недоступное действие — 409, неизвестное — 422.
- Сбой диалога или батча задание не останавливает: диалог получает ошибку из `errors` запуска (`failed`), очередь идёт дальше. Повторы 429/5xx с паузами делает клиент модели, очередь их не дублирует. Задание закончено, когда в очереди нет диалогов: `failed`, если с ошибкой все, иначе `done`. Запуск батча, отменённый через `POST /api/runs/{id}/cancel`, ставит задание на паузу с `note`.
- `throughput_per_min` и `eta_s` — по скорости последних 3 завершённых батчей (`eta_basis`: «по скорости последних 3 батчей», «последнего батча», «нет завершённых батчей» — тогда `null`); `eta_s` только у `queued` и `running`.
- `rate_limit` — `CQA_LLM_RPM` (запросов в минуту, `0` — без лимита; окно 60 с в клиенте модели держит темп каждой попытки) и `CQA_LLM_MAX_PARALLEL`. Остаток лимита провайдер не сообщает, поэтому его нет.
- Перезапуск сервера: состояние в SQLite (`batch_jobs`, `batch_items`, `batch_runs`). Задания `queued` и `running` встают на паузу с `note` «Сервер перезапускался…», диалоги прерванного батча — снова в очереди. Само задание не продолжается: после перезапуска могли смениться модель, ключи и режим данных (`CQA_LLM_MODE`, `CQA_ALLOW_REAL_DATA`), а оценка тратит деньги — продолжает человек кнопкой. `resume` и `retry` стирают `note`.
## История оценок и повторная проверка (review-workflow, history)

Таблица `results` только растёт: каждый ответ модели, ручной ответ и возврат прежней оценки — новая строка, итог берёт последнюю строку текущего смысла пары. Строка помнит запуск (`run_id`, `null` — ручной ответ или строка до появления колонки); кто ответил — `CriterionResult.model`.

**Повторная проверка.** `POST /api/runs` с `force: true` оценивает выбранные пары заново, даже если у них есть текущий результат; новый ответ становится текущим, прежний остаётся в истории. Пары, которые держит человек, пропускаются: текущий ответ ручной (`model: "вручную"`) или по паре текущего смысла есть апелляция на рассмотрении или решение (`confirmed`, `changed`). Их число — `skipped` запуска. Без `force` пропусков нет (`skipped: 0`): пары с ответом просто не входят в план. `force` без списка `dialogs`, если заново пойдёт больше 5 диалогов, требует `confirm: true`, иначе 422 «Подтвердите перезапуск N диалогов» и запуск не создаётся; явный список — уже подтверждение. «Оценить моделью» на карточке диалога — `{"dialogs": ["<id>"], "force": true}`.

**Перепроверка другой моделью или с другими настройками.** `override: {"evaluator"?: "llm" | "jev", "llm_provider"?: "<код провайдера>", "verifier"?: "jev" | "<код провайдера>" | null}` — поля поверх текущего режима только на этот запуск, неуказанное — как в режиме; сохранённый режим (`GET /api/config`) не меняется. `override` (даже `{}`) — всегда повторная проверка, как `force`. Ошибки 422 без создания запуска: неизвестный провайдер — «override.llm_provider: нет провайдера X» / «override.verifier: нет провайдера X»; ошибка конфигурации — «Перепроверка: <текст>», например «Перепроверка: Нет ключа Jev для оценки только Jev в режиме live…»; лишнее поле или `evaluator` не из списка — 422 FastAPI. `model` запуска — модель режима с `override`, `override` запуска — как прислан (поля, которые указаны).

`apply`: `replace` (по умолчанию) — новые ответы сразу текущие; `compare` — тоже повторная проверка, но ответы теневые: строки с `run_id` запуска и `shadow`, итог, очередь и отчёты их не видят, они есть в истории (`shadow: true`) и в `GET /api/runs/compare`. Текущим теневой ответ делает `POST /api/results/{id}/restore` (по критерию) или `POST /api/runs/{id}/adopt` (весь запуск или часть по `dialogs` и `criteria`): копия последней теневой строки пары становится текущей. `adopt` пропускает и считает в `skipped` пары, которые держит человек (как при `force`), и ответы прежнему смыслу критерия; запуск `replace` — 409 «Запуск N заменял ответы сразу: принимать нечего», неизвестный — 404. Ручные ответы и решения модель не перезаписывает ни при `replace`, ни при `adopt`.

**Статусы диалогов.** RunDialog: `{"id": "call-024", "status": "queued" | "evaluating" | "done" | "error" | "skipped" | "cancelled", "error": null | "<текст>", "done": 7, "total": 8, "skipped": 0}` в порядке очереди. `total` — критериев к оценке, `done` — получено ответов, `skipped` — пар диалога, которые держит человек. `error` — текст сбоя диалога (`status: "error"`) или «нет ответа модели, ждёт оценки: <id>, …» при `done` < `total`. `skipped` — все выбранные пары диалога держит человек (только при `force`), `cancelled` — запуск отменён или сервер перезапущен до оценки диалога. `GET /api/state`: `eval_status` диалога — RunDialog без `id`, с `run_id`, из последнего запуска, где диалог был; `null` — запусков с ним не было.

**История.** `GET /api/dialogs/{id}/history` → `{"<cid>": [{"id": 41, "created": "<ISO>", "run_id": 3 | null, "version": 3, "model": "qwen3-6" | "вручную" | null, "a": ответ, "why": "…" | null, "ev": [9], "current": true, "stale": false, "shadow": false, "override": null | {…}}]}`, новые первыми. `current` — строка, которую считает итог (одна на критерий или ни одной, теневая никогда); `shadow` — теневой ответ запуска `compare`; `override` — настройки перепроверки запуска, давшего ответ (`null` — режим как есть или ручной ответ); `stale: true` — ответ прежнему смыслу критерия или критерию, которого нет в текущем чек-листе. Решения проверяющего и апелляции в истории не повторяются: они в `appeals`.

**Возврат прежней оценки.** `POST /api/results/{id}/restore` добавляет копию строки (тот же ответ, `model`, `run_id`) последней — она становится текущей, история не переписывается. Ответ — CriterionResult. 404 — нет такой строки. 409 с причиной: апелляция по паре на рассмотрении («По критерию 04 есть апелляция на рассмотрении: a3»), оценка дана прежнему смыслу критерия, оценка уже текущая. Теневая строка восстанавливается обычной (не теневой).

**Запуски.** `GET /api/runs` → `[{"id": 4, "created": "<ISO>", "status": "done", "model": "qwen3-6" | null, "checklist_version": 3 | null, "total": 16, "done": 16, "cost": 0.016, "errors_count": 0, "force": true, "skipped": 1, "apply": "replace" | "compare", "override": null | {…}}]`, последние 50, новые первыми. `model` — `mode.model` в момент запуска (с `override`); `null` — запуск до появления колонки.

**Сравнение запусков.** `GET /api/runs/compare?a=3&b=4` → `{"a": 3, "b": 4, "pairs": 16, "agree": 0.875, "criteria": [{"cid": "04", "pairs": 2, "agree": 0.5, "mean_step_diff": 1.0}], "diffs": [{"dialog": "call-024", "cid": "04", "a": 15, "b": 10}]}`. Учитываются пары «диалог, критерий», отвеченные в обоих запусках, у пары — последняя строка запуска; ответ сравнивается как есть (флаг — объект целиком), без решений проверяющего. `agree` — доля совпавших, `null` без общих пар. `mean_step_diff` — у шкалы средняя разница в ступенях (`steps` текущего чек-листа), пары с `na` не в счёт; у остальных `null`. `criteria` — в порядке чек-листа. Теневые ответы входят. «Сравнить модели»: запуск `{"force": true}` или прежний и запуск `{"apply": "compare", "override": {"llm_provider": "<другой>"}}` того же набора.
