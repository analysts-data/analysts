# Регламент контрольного часа и защиты

Сервер — `make run` на `http://127.0.0.1:8000`. Все команды из корня репозитория. Решения принимает капитан, остальные выполняют по шагам и докладывают в общий чат.

## Контрольный час (8 ноября)

| Время | Что делаем | Готово, когда |
| --- | --- | --- |
| 10:00 | Свежий клон по README: `scripts/fresh_clone.sh <репозиторий>`, затем `make e2e ARGS=--runxfail` | клон запускается без правок, все шаги e2e зелёные или известны |
| 10:30 | Публикация только с одобрения капитана: `scripts/publish.sh <owner/repo>`, ссылку отправляем организаторам | анонимный клон работает, ссылка в чате организаторов |
| 11:00 | Вводим `group_id`, объявленный организаторами (не подбираем), «Получить набор» на экране «Диалоги» | `{added, skipped}` на экране, `skipped` объяснён журналом сервера |
| 10:45 | Файл DEV для организаторов: `make results SET=dev`, затем `git add results/dev && git commit -m "chore(results): dev" && git push origin main` | `results/dev/results.json` виден в `main` на GitHub |
| 11:00–11:45 | Пакет в порядке приоритета, наблюдение за ошибками и очередью на проверку (ниже); без интерфейса — `make results SET=prod GROUP=<group_id> ARGS=--evaluate` («Одной командой») | все диалоги оценены, `errors` пуст |
| сразу после пакета, не позже 11:45 | Файл контроля: `make results SET=prod GROUP=<group_id>`, проверка (ниже), затем `git add results/prod && git commit -m "chore(results): prod" && git push origin main` | код выхода 0, «записей 10», `results/prod/results.json` виден в `main` на GitHub до 12:00 |
| 11:45 | `git tag -a v1.0 -m "контрольный набор"` и `git push origin v1.0`; `make backup` | тег в репозитории, копия базы в `data/backup/` |
| 12:00 | Стоп-код: код не меняется. Дальше только обработка данных и смена чек-листа через интерфейс | `make check` у ветки поверх `origin/main` падает со «стоп-код 12:00» |

До 11:45 в код идут только блокирующие исправления: те, без которых набор не обрабатывается. Остальное записываем и не трогаем.

### Пакет на контроле

1. Первая порция одним `POST /api/runs`: все звонки и часть чатов каждого языка (фильтр очереди `#/queue?ch=call`, затем `lang`). Диалоги обрабатываются в переданном порядке.
2. `scripts/demo.py pick > pick.json` — подбор диалогов для защиты. Если выбранные диалоги ждут оценки, запускаем их отдельным запуском первыми.
3. Остальной набор — кнопка «Оценить» без фильтров.
4. Следим за `GET /api/runs/{id}`: `done/total`, `cost`, `eta_s`, `errors`. Ошибку `429` и таймаут сервер повторяет сам; `ConfigError` — ключ или профиль в `.env`, зовём капитана.
5. Очередь «Нужна проверка»: расхождение моделей и проваленное основание решает специалист в карточке («Оставить» или «Принять», причина обязательна, запись `kind: "review"`). Грубые ошибки просматриваем и снимаем отметкой `{"reviewed": true}` — «Отметить проверенным». Если у реплики звонка нет `s`, слушаем запись по ссылке «Открыть в плеере» (`/api/dialogs/{id}/player`).
6. Остановить пакет: «Остановить» (`POST /api/runs/{id}/cancel`). Повторный «Оценить» продолжает с места остановки, готовые ответы не пересчитываются.

### Файл результатов (формат JSON 1.0)

`make results SET=prod GROUP=<group_id>` берёт ровно `conversation_id` из снимка `data/raw/<group_id>.json`, который сервер сохранил при «Получить набор», ответы и решения — из базы, как интерфейс. Если набор загружали файлом: `make results SET=prod ARGS="--source <файл>"`.

### Одной командой: набор, оценка, файл

```bash
make results SET=prod GROUP=<group_id> ARGS=--evaluate        # контроль
make results SET=dev ARGS=--evaluate                           # DEV из CQA_EVAL_DATASET
make results SET=prod ARGS="--evaluate --source <файл>"        # набор файлом
```

1. Набор загружается в базу, как в интерфейсе: `GROUP` — «Получить набор» (ссылка из интерфейса или `CQA_ORG_API_URL`, тот же снимок `data/raw/<group_id>.json`), файл — «Загрузить JSON». Печатается `набор …: {added, skipped}`.
2. Модель из `.env` и режима интерфейса оценивает пары набора без ответа текущего чек-листа, по `CQA_LLM_MAX_PARALLEL` сразу, в порядке набора. Каждые 5 секунд строка `оценка done/total, ошибок N, $cost`, в конце — строки ошибок. Звонки уходят модели только с `CQA_ALLOW_REAL_DATA=1` (ставит человек).
3. Затем выгрузка и проверка, как ниже; код выхода тот же. Повторный запуск продолжает: готовые ответы не пересчитываются.

Сервер `make run` можно не останавливать: SQLite в режиме WAL, запись ждёт другую до 5 секунд, интерфейс видит ответы после обновления. Не нажимайте «Оценить» в интерфейсе одновременно: оба процесса оценят одни и те же пары. API организаторов недоступен, а снимок уже есть — `ARGS="--evaluate --source data/raw/<group_id>.json"`.

Проверка перед push:

1. Код выхода 0. Код 1 — строки `FAIL` в выводе: повтор id, неполный `ok` или не 10 записей. Файл записан всё равно.
2. Строки `error <id>: <причина>` — диалог не оценён по всем критериям. Если успеваем, «Оценить» этот диалог и повторить `make results`; иначе пушим как есть: ошибка честнее нуля и пропуска.
3. `model` в выводе: модели из ответов в базе, второе мнение добавляется само. Поправить можно `ARGS='--model-name "..." --mode hybrid'`, команду — `ARGS="--team ..."`.
4. В 11:50 пушим то, что есть: локального файла и commit без push организаторам недостаточно.

## Защита

### Режим демо: живая модель, запасной — записи

- Основной вариант — живой режим: `.env` по сценарию 4 (`CQA_LLM_MODE=live`, ключ alem), затем `make run`. Демо идёт на синтетических данных: набор защиты `tests/e2e/fixtures/defence_set.json` через «Загрузить JSON» (или DEV), обезличивание включено (`CQA_ANONYMIZE=1` — умолчание). Так после правки чек-листа жюри видит настоящий вызов модели: «Оценить набор» считает критерии заново с живым прогрессом и ценой.
- Запасной вариант без сети или ключа — `make demo`: сервер на записанных ответах (`CQA_LLM_MODE=replay`), отдельная база `data/demo.db`, набор защиты уже загружен и оценён. Шаг замены критерия показываем на сохранённых ответах и говорим это вслух.
- Репетиции — на `make demo`, чтобы не тратить общий лимит 120 запросов в минуту провайдера; живой прогон — один, накануне.

### Критерий готовности

- Выбранные `pick` диалоги оценены по всем критериям текущей версии (нет «Ждёт оценки»).
- Пакет завершён: `done == total`, `errors == []`. Если по `eta_s` пакет не успевает к демонстрации, следующую порцию не запускаем до конца выступления: лимит провайдера 120 запросов в минуту общий, и живая замена критерия не должна делить его с пакетом.

### Проверка за 15 минут

```bash
scripts/demo.py check --pick pick.json --run <id пакета> --call <id звонка> \
  --draft tests/e2e/fixtures/replacement_criterion.json
```

Скрипт проверяет полноту `res` выбранных диалогов, завершённые запуски, запись звонка (302 и 200/206, ссылку не печатает), `mode` (модель и место обработки) и черновик критерия, код выхода ненулевой при любом провале. Ручные пункты он печатает списком: переключение роли, плашка режима в шапке, черновик открыт во второй вкладке.

### Подбор диалогов

`scripts/demo.py pick` выбирает по одному контрольному диалогу на шаг: «грубая ошибка» (флаг с основанием), «N/A» (условие выполнено, есть применимые критерии), «апелляция» (шкала ниже максимума с основанием, без апелляции на эту пару), «звонок» (у реплик-оснований есть `s`). Из подходящих берётся самый короткий. Если подходящего нет, берётся диалог DEV из таблицы защиты (`p1-ru-022`, `p1-ru-025`, `p1-ru-003`), а для звонка — `p4-ru-002`, и выступающий говорит вслух фразу из поля `say`: «В контрольном наборе звонков нет, показываем звонок из DEV».

### Живая замена критерия

1. Чек-лист → критерий → вставляем заготовленный черновик из второй вкладки (тот же текст, что `tests/e2e/fixtures/replacement_criterion.json`).
2. «Сохранить как vN»: открытый диалог показывает «Ждёт оценки» по заменённому критерию, итог предварительный.
3. «Оценить набор» на открытом диалоге: прогресс `done/total`, `cost`, `eta_s` из `GET /api/runs/{id}`. Пакет всего набора закончен заранее, поэтому запуск идёт без очереди.
4. Апелляция на заменённый критерий закрывается (`closed`), исходная оценка остаётся в истории.

### Репетиции крайних случаев

- «Итог не рассчитывается»: все применимые критерии получили N/A, на месте итога прочерк. Фраза: «Итог не рассчитывается: ни один критерий с весом не применим к этому разговору, это честнее, чем ноль или сто».
- «Новый итог отличается, исходная оценка видна»: после решения по апелляции карточка показывает исходный ответ модели, решение с автором и причиной и новый итог. Фраза: «Исходная оценка модели не перезаписывается: видно, кто, когда и почему её изменил».

### Запасной путь

- Сеть или провайдер упали: сервер на копии базы из `make backup` (`CQA_DB_PATH=data/backup/cqa-<HHMM>.db make run`), ответы модели не нужны.
- Ноутбук не показывает экран: видео репетиции.
- Нет сети в зале: точка доступа с телефона.

### Если критерий заменяют организаторы

После 12:00 код не меняется. Организаторы диктуют критерий, мы вводим его в редакторе чек-листа как данные (название, текст, тип, вес, N/A с условием, канал), сохраняем новую версию и запускаем «Оценить набор»: оцениваются только изменённые критерии. Отпечаток смысла пересчитывает ровно этот критерий, остальные ответы берутся из сохранённых.
