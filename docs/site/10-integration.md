# Интеграция по API

Всё, что делает интерфейс, доступно по HTTP: интерфейс сам работает только через этот API. Раздел описывает типовые сценарии для ИТ брокера: загрузить диалоги, запустить оценку, забрать ответы, апелляции и отчёты. Полный список методов с параметрами и схемами — [Справочник API](api), он строится из работающего сервера и всегда совпадает с кодом.

## Основы

- Базовый адрес — адрес сервера, например `http://127.0.0.1:8000`. Все методы лежат под `/api`.
- Формат — JSON в UTF-8, заголовок `Content-Type: application/json`. Исключения: загрузка набора файлом (сырое тело файла), выгрузки чек-листа и отчёта в CSV, Markdown и HTML.
- Схема OpenAPI 3: `GET /api/openapi.json`. По ней можно сгенерировать клиент на любом языке.
- Проверка, что сервер жив: `GET /api/health` возвращает `{"ok": true}`.
- Время в ответах — по Астане (UTC+5), формат `ДД.ММ ЧЧ:ММ` в полях `at` и `decidedAt`.

### Доступ

Входа и токенов в текущей версии нет: сервер рассчитан на закрытый контур брокера. Ставьте его во внутреннюю сеть или за обратный прокси с вашей аутентификацией. Кросс-доменные запросы браузера разрешены только с доменов `*.dynamics.com`, см. [Встраивание в Dynamics 365](dynamics).

Скоро: токен доступа к API.

## Сценарий 1. Загрузить диалоги

Есть три способа, все возвращают `{"added": N, "skipped": M}`. Диалог с уже известным `id` пропускается, битые записи входят в `skipped`, причины пишутся в журнал сервера. Оценка после загрузки сама не запускается.

**По `group_id` из API источника** (адрес источника задан на сервере в `CQA_ORG_API_URL` или в интерфейсе; браузер и клиент его не видят):

```bash
curl -X POST http://127.0.0.1:8000/api/datasets \
  -H 'Content-Type: application/json' -d '{"group_id": "DEV"}'
```

**Файлом JSON** — тело запроса и есть файл, без multipart:

```bash
curl -X POST http://127.0.0.1:8000/api/datasets/upload --data-binary @set.json
```

Формат файла — конверт источника. Канал `agent chat` — чат, `voice call` — звонок; роль `speaker`: `client`, `operator`, `bot`, `system`.

```json
{
  "isSuccess": true,
  "error": null,
  "data": {
    "dataset_group_id": "DEMO",
    "total_records": 1,
    "records": [
      {
        "conversation_id": "demo-chat-1",
        "channel": "agent chat",
        "language": "RU",
        "audio_url": null,
        "transcript": [
          {"timestamp": "00:00", "speaker": "client", "text": "Здравствуйте, не приходит код подтверждения."},
          {"timestamp": "00:20", "speaker": "operator", "text": "Здравствуйте! Меня зовут Анна. Проверю, минуту."}
        ]
      }
    ]
  }
}
```

**Текстом одного диалога** — строки `Роль: текст`. Клиент — `Клиент`, `Client`, `Customer`; оператор — `Оператор`, `Operator`, `Менеджер`; бот — `Бот`, `Bot`; событие — `Система`, `System`. Строка без роли продолжает предыдущую реплику. Без реплики оператора — 422.

```bash
curl -X POST http://127.0.0.1:8000/api/dialogs/text \
  -H 'Content-Type: application/json' \
  -d '{"title": "Код не приходит", "ch": "chat", "text": "Клиент: Не приходит код.\nОператор: Здравствуйте! Проверю."}'
# {"id": "paste-1"}
```

## Сценарий 2. Запустить оценку и дождаться результата

`POST /api/runs` оценивает пары «диалог — критерий», у которых ещё нет ответа текущей версии чек-листа. `dialogs` задаёт порядок (первыми идут нужные срочно), `null` — все диалоги; `criteria` ограничивает критерии, `null` — все. Одновременно идёт один запуск: второй получит 409.

```bash
curl -X POST http://127.0.0.1:8000/api/runs \
  -H 'Content-Type: application/json' -d '{"dialogs": ["paste-1"], "criteria": null}'
# {"run_id": 7}

curl http://127.0.0.1:8000/api/runs/7
# {"done": 4, "total": 10, "cost": 0.0, "calls": 4, "eta_s": 12, "errors": [], "status": "running"}
```

`status` — `running`, `done` или `cancelled`; `errors` — строки с причиной по диалогам, которые не удалось оценить. Остановить запуск — `POST /api/runs/{id}/cancel`: диалоги в работе завершаются, новые не начинаются. Повторный запуск продолжает с места остановки, готовые ответы не пересчитываются.

```python
import time
import httpx

api = httpx.Client(base_url="http://127.0.0.1:8000/api", timeout=30)

run_id = api.post("/runs", json={"dialogs": ["paste-1"], "criteria": None}).raise_for_status().json()["run_id"]
while (progress := api.get(f"/runs/{run_id}").json())["status"] == "running":
    print(f"{progress['done']}/{progress['total']}, осталось около {progress['eta_s']} с")
    time.sleep(2)
print(progress["status"], progress["errors"])
```

## Сценарий 3. Забрать ответы и посчитать итог

`GET /api/state` возвращает всё, что видит интерфейс: текущий чек-лист, версии, диалоги с ответами по критериям (`res`), апелляции и решения, режим оценки. Ответ по критерию — объект CriterionResult: `a` (ответ), `why` (обоснование), `ev` (номера реплик-оснований), `quote`, `tag` (причина снижения), `better` (как сказать лучше), `evFail`, `alt` (второе мнение), `model`, `calls`, `cost`, `ms`. Критерия без записи в `res` ещё нет: он ждёт оценки.

Итог сервер не хранит: он считается по формуле чек-листа с учётом последнего решения человека. Формула и правила — [Чек-лист и расчёт итога](checklist). Пример на Python:

```python
from decimal import ROUND_HALF_UP, Decimal

state = api.get("/state").json()
criteria = {c["id"]: c for c in state["checklist"]["criteria"]}


def answer(dialog: dict, cid: str):
    """Последнее решение по паре (подтверждено или изменено), иначе ответ модели."""
    decided = [x["to"] for x in state["appeals"]
               if x["dlg"] == dialog["id"] and x["cid"] == cid
               and x["status"] in ("confirmed", "changed") and x["to"] is not None]
    return decided[-1] if decided else dialog["res"][cid]["a"]


def total(dialog: dict) -> float | None:
    weight = gained = 0.0
    for cid in dialog["res"]:
        c, a = criteria.get(cid), answer(dialog, cid)
        if c is None or c["type"] == "flag" or a == "na":
            continue
        share = (1.0 if a == "yes" else 0.0) if c["type"] == "bool" else a / max(c["steps"])
        weight += c["w"]
        gained += c["w"] * share
    if not weight:
        return None  # итог не рассчитывается: нет применимых критериев
    return float(Decimal(f"{100 * gained / weight * 100:.12g}").quantize(Decimal(1), ROUND_HALF_UP)) / 100


for d in state["dialogs"]:
    print(d["id"], d["ch"], d["lang"], total(d))
```

Для сдачи результатов в формате JSON 1.0 (итог, ответы по критериям и основания по каждому диалогу) есть готовая команда `make results`, см. [Контрольный час](control-hour).

## Сценарий 4. Ручной ответ, апелляция и решение

Ручной ответ специалиста заменяет ответ модели по критерию, повторная оценка его не трогает:

```bash
curl -X PUT http://127.0.0.1:8000/api/dialogs/paste-1/answers/04 \
  -H 'Content-Type: application/json' \
  -d '{"a": 15, "reason": "Срок ответа назван в реплике 6", "by": "Специалист КК"}'
```

Апелляция оператора и решение проверяющего. Комментарий апелляции — не короче 10 символов, просимый ответ должен отличаться от текущего, по паре может быть одна апелляция на рассмотрении. Причина решения обязательна, не короче 5 символов. Для грубой ошибки `ask` и `to` — объект `{"<вид нарушения>": true | false}` по всем видам.

```bash
curl -X POST http://127.0.0.1:8000/api/appeals \
  -H 'Content-Type: application/json' \
  -d '{"dlg": "paste-1", "cid": "04", "ask": 20, "ev": [6], "comment": "Решение дано полностью", "by": "Оператор"}'
# {"id": "a1", "kind": "appeal", "status": "pending", ...}

curl -X POST http://127.0.0.1:8000/api/appeals/a1/decision \
  -H 'Content-Type: application/json' \
  -d '{"to": 20, "reason": "Ответ полный, срок назван", "reviewer": "Проверяющий"}'
```

Решение по расхождению моделей или проваленному основанию без апелляции — `POST /api/decisions` с полями `dlg`, `cid`, `from`, `to`, `reason`, `reviewer`. Исходный ответ модели не меняется никогда: решения хранятся рядом и видны в истории.

## Сценарий 6. Режим оценки

`GET /api/config` показывает режим без ключей: основная модель, провайдеры, второе мнение, обезличивание, разрешение реальных звонков. `PUT /api/config` меняет режим без перезапуска, `PUT /api/providers/{id}` заводит провайдера модели со своим ключом, `POST /api/providers/{id}/check` проверяет связь синтетическим запросом. Ключи только записываются и ни в одном ответе не возвращаются. Во время запуска оценки любое изменение режима получает 409.

## Коды ответов и ошибки

Ошибка приходит с телом `{"detail": "<текст по-русски>"}`. Ошибка проверки тела или параметров (FastAPI) — 422 с `detail` в виде списка `[{"loc": [...], "msg": "...", "type": "..."}]`.

| Код | Когда | Что делать |
| --- | --- | --- |
| 200 | Успех | — |
| 302 | Ссылка на запись звонка или плеер | Перейти по `Location`; ссылка живёт недолго, не сохраняйте её |
| 404 | Нет диалога, критерия, апелляции, запуска, версии чек-листа; у диалога нет записи | Проверить идентификатор |
| 409 | Уже идёт запуск оценки; по паре уже есть апелляция на рассмотрении или решение; апелляция уже рассмотрена; черновик чек-листа основан на старой версии; удаляется провайдер, выбранный основной моделью или вторым мнением | Дождаться конца запуска, обновить данные и повторить |
| 422 | Неверное тело или параметры, ответ не из допустимых, пустая причина решения, ошибка конфигурации режима | Исправить запрос, текст ошибки называет поле |
| 502 | Не ответил внешний сервис: API источника, ссылка на запись, разбор звука | Повторить позже; прежние данные не меняются |
| 503 | Оценщик или загрузка наборов не подключены | Проверить настройки сервера |

Ошибки модели при оценке (429, таймаут) сервер повторяет сам; что не удалось, попадает в `errors` запуска, а не в код ответа.
