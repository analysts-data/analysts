## Что строим

Один процесс: FastAPI раздаёт API и статический интерфейс `<cqa-app>`. Интерфейс уже нарисован в прототипе: очередь диалогов, карточка, апелляции, редактор чек-листа, аналитика, обучение. Сервер подменяет моки прототипа настоящими данными той же формы.

```
организаторы ─► ingest ─► segments и время ─► SQLite ◄─ appeals и решения
                                   │
                    чек-лист (версии, данные)
                                   ▼
          обезличивание ─► оценка по критерию (LLM) ─► проверка оснований ─► кэш
                                   │                           │
                         второе мнение (Jev или нет)     results в SQLite
                                   ▼
            GET /api/state ─► <cqa-app>: scoring.js, очередь, карточка, аналитика
```

## Стек и почему

| Слой | Выбор | Почему не альтернатива |
| --- | --- | --- |
| Сервер | Python 3.12, FastAPI, Pydantic v2, uv | Команда и замеры уже на Python; FastAPI даёт валидацию и OpenAPI без кода. Django тяжелее, Node раздвоил бы стек |
| Хранилище | stdlib `sqlite3`, один файл `data/cqa.db` | ORM не нужен на пяти таблицах; Postgres требует сервера |
| HTTP наружу | `httpx` async, семафор и ограничитель запросов в минуту | Нужны параллельность и лимит 120 запросов в минуту у провайдера в РК |
| Интерфейс | ES-модули без сборки и CDN, `<cqa-app>` | Требование Dynamics 365; прототип уже на чистом JS. React добавил бы сборку |
| Итог | `web/js/scoring.js` — единственная реализация | Итог нужен только интерфейсу. Сервер его не считает, поэтому дублирования нет. Векторы общие |
| Тесты | pytest, respx, node --test, pytest-playwright | Один раннер для сервера и сквозных тестов, без Jest |
| Качество | ruff, mypy, `openspec validate --strict` | Быстро и без настройки |
| Модели | OpenAI-совместимый клиент, сценарий из `.env` | Смена провайдера — одна переменная. Пять сценариев в `docs/plan.md` команды |

## Процесс одной задачи

1. `scripts/wt.sh new <change> <slug>` создаёт worktree `.worktrees/<change>-<slug>` и ветку `feat/<change>-<slug>`. Файлы агентов и план (`openspec/`, `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.pi/`) в git не хранятся: скрипт подключает их символическими ссылками, и `tasks.md` становится общей доской задач.
2. Агент читает `AGENTS.md`, изменение OpenSpec и `design/contract.md`, затем запускает `/opsx:apply <change>` (Claude) или промпт `opsx-apply` (pi).
3. На каждую задачу: тест, красный прогон, код, зелёный прогон, рефакторинг, `make check`, коммит, `git push`.
4. Первый пуш открывает черновой PR. Когда группа задач готова: rebase на `main`, `make check`, PR в ready.
5. CI гоняет `make check` и `make e2e`. Ревьюер другой модели оставляет замечания через `gh pr review`.
6. Оркестратор делает squash merge, worktree удаляется. После последней группы — `openspec archive <change>`.

## Harness

| Проверка | Где | Что ловит | Порог |
| --- | --- | --- | --- |
| `make check` | локально и CI | ruff, mypy, модульные и интеграционные тесты без сети, `node --test`, `openspec validate`, секреты, защищённые пути | всё зелёное |
| `make e2e` | локально и CI | Сценарий защиты в Playwright на записанных ответах модели | без ошибок, до 2 минут |
| `make eval` | вручную, с ключом | Совпадение с эталоном по языкам и критериям, грубые ошибки, N/A, основания, стабильность; без порога — расхождения второго мнения и дробление тегов | пороги в `eval/thresholds.yaml` |
| Отложенные критерии | вручную | Замена критерия: пять критериев с закрытым эталоном вне репозитория | не ниже 85% |
| Свежий клон | перед публикацией | Запуск по README без правок, история без секретов | без ручных шагов |

Записанные ответы модели (`tests/cassettes/`) делают тесты быстрыми, бесплатными и детерминированными. Записывает их только `make record` с живой моделью на синтетических чатах.

Защищённые пути (`eval/gold/`, `eval/thresholds.yaml`, `eval/baseline.json`, `design/contract.md`, `design/ports.md`, `.github/`) проверяет `scripts/protected_paths.sh`: PR без метки `human-ok` с правкой этих путей падает. Тот же скрипт не пускает в git файлы агентов и план. `openspec validate --all --strict` выполняется в локальном `make check`, потому что в CI каталога `openspec/` нет.

## Что режем при отставании

Сначала процесс, потом функции. Если M1 в 19:00 не пройден:

1. Ревью другой моделью остаётся только у PR, которые трогают промпт, контракт, `scoring.js` и эталон. Остальные сливаются по зелёному `make check`.
2. `make e2e` уходит из CI: его запускают локально перед переводом PR в ready.
3. Если к 22:00 экраны `cqa-web-ui` не собраны, подключаем прототип `design/cqa-v3/index.html` как есть. Моки `CL0`, `D`, `AP` заменяются на `GET /api/state`, действия — на вызовы `api.js`. Поля прототипа совпадают с контрактом, это около 200 строк правок.

Затем функции:

1. Раздел «Обучение»: подсказка «Как сказать лучше» остаётся в карточке.
2. Адресат у повторяющихся причин: остаются счётчики.
3. Волна записи: остаётся плеер с переходом к моменту.
4. Второе мнение (Jev или самопроверка): остаётся проверка оснований.

Не режем: переход к реплике и моменту записи, N/A и пересчёт, грубые ошибки наверху, апелляцию, редактор чек-листа, стоимость оценки.

### Общие правила чек-листа

`rules` — данные, но их смена меняет отпечаток всех критериев и отправляет весь набор на переоценку (`review-workflow`, решение 4). На защите правила не трогаем. Поэтому их пишут так, чтобы замена критерия не требовала их править, и замораживают до 22:00, до `make record` и эталонного прогона. Начальный текст для `tests/fixtures/checklist_v3.json` (`bootstrap-harness`, задача 4.1), по PDF организаторов:

```text
Один чек-лист применяется к чатам и звонкам на русском, казахском и английском.
N/A ставь только там, где он разрешён и выполнено его условие. «Нет» — действие было нужно, но оператор его пропустил или выполнил неправильно. Общий вопрос о тарифах не требует идентификации; если проверка личности требовалась перед защищённым действием и не подтверждена, ставь «Нет».
Для шкалы выбирай одну из указанных ступеней.
Время ответа, теги и вложения оценивай, только если этого прямо требует текст критерия.
Основание — конкретная реплика или системное сообщение. Для пропущенного действия укажи участок, где оно ожидалось. Для N/A назови выполненное условие.
Предложение услуги в обход компании — предложение перевести деньги оператору лично или просьба дать личный номер для платной консультации. Достаточно самого предложения, согласие клиента не нужно.
```

### Отложенные критерии

Пять критериев пишет человек, который не трогал промпт. Они покрывают формы замены, которые вероятнее всего предложит жюри:

1. Время: «Оператор ответил клиенту в течение 3 минут после его первого сообщения», `bool`, N/A, если оператор не подключился. Проверяет паузу в строке реплики.
2. Срок ответа: «Если вопрос передан специалистам, оператор назвал срок ответа», `bool` с N/A. Это пример со слайда 10.
3. Только звонки: «Оператор назвал компанию в приветствии», `channel: call`.
4. Нестандартная шкала: три ступени 10, 5, 0, например «Оператор обращается к клиенту по имени и учитывает историю обращения».
5. Звук: «Оператор говорит спокойно и доброжелательно». В частых вопросах задания сказано, что для интонации нужен звук. Ждём осторожного ответа с пометкой в обосновании (правило 10 промпта), а не уверенной оценки тона.

Тот же прогон проверяет редактор: новая секция, сумма весов не 100, смена веса без вызовов модели.

## ML и второе мнение

Решение от 7 ноября: свои модели не обучаем, кластеризацию не строим. ML в системе — это модель с рассуждением, второе мнение и измеримый эталон.

| Почему | Что это значит для кода |
| --- | --- |
| На DEV 65 диалогов и 520 ответов, решений проверяющих за хакатон будут единицы | Обученный классификатор или кластеризация на таком объёме — шум |
| После стоп-кода организаторы заменяют критерий без правки кода | У классификатора для нового критерия нет ни разметки, ни весов. LLM берёт критерий как данные, это проверяет `make eval-holdout` |
| Слайд 10: доверие строится на критерии, причине, реплике и моменте записи | Классификатор даёт метку без цитаты. Модель даёт `ev` и `quote`, код их проверяет |
| Свежий клон по README, тесты без сети | sklearn или sentence-transformers тянут PyTorch и ломают оба условия |

### Второе мнение без Jev

В сценарии 4 (данные в РК) Jev выключен, `mode.verifier` равен `null`. Сигнал «на проверку» берётся из четырёх источников по возрастанию цены.

| Источник | Что делает | Где | Когда |
| --- | --- | --- | --- |
| Проверка оснований кодом | Реплика существует, цитата есть в тексте, ответ разрешён типом; после повтора `evFail` | `llm-evaluation`, уже в плане | Волна 1 |
| Самопроверка `CQA_VERIFIER=self` | Вторая реализация `Verifier`: та же модель с рассуждением, обратная постановка «найди реплики, где критерий нарушен», та же схема JSON. Расхождение пишется в `alt` и уходит в очередь на проверку, флаг ставится, если нашла любая попытка. Вызовов вдвое больше: DEV за ~11 минут вместо ~6 при лимите 120 запросов в минуту | `llm-evaluation`, после M2 | Волна 3, включается по отчёту `make eval` |
| Другая модель у провайдера в РК | Если в `/v1/models` у `llm.alem.ai` есть другое семейство, это второе мнение с некоррелированными ошибками. Подключается как профиль клиента, без нового кода | Человек с ключом | До 19:00 |
| Вероятности токенов | Если прокси отдаёт `logprobs`, вероятность токена ответа — бесплатный сигнал неуверенности. У моделей с рассуждением калибровка плохая, порог только по эталону | Человек с ключом проверяет поддержку, код только если она есть | Проверка до 19:00, код после M3 |

`make eval` печатает для включённого второго мнения долю расхождений и долю ошибок основной модели, на которых второе мнение разошлось. Самопроверка остаётся включённой на контроле, только если ловит ошибки на эталоне и укладывается в окно 11:00–11:45. Без неё плашка честно показывает `verifier: null`, очередь на проверку строится из проваленных оснований.

### Паттерны и решения проверяющих

- Повторяющиеся причины: счётчик по точному `tag` с адресатом правки, как в `analytics-coaching`. От дробления тегов защищает промпт: короткий тег без деталей диалога. `make eval` печатает число повторяющихся и одиночных тегов; если одиночных больше, добавляем склейку по токенам в `web/js/analytics.js`, без зависимостей.
- Обучение системы на решениях проверяющих идёт только через данные, других петель после стоп-кода нет: решение с причиной → правка `rules` или текста критерия в редакторе → новая версия → переоценка по одному вызову на диалог, остальное из кэша.
- Чтобы видеть, где править: `qualityStats` отдаёт долю изменённых решений по критерию и языку, экран аналитики показывает её таблицей со ссылками в очередь.
- Не делаем: подстановку прошлых решений в промпт как примеров (ломает кэш и кассеты по хешу запроса, переносит текст одного диалога в оценку другого), обучение предсказателя отмены решения, эмбеддинги и кластеризацию тегов.

Ответ жюри на вопрос «где ML»: модель с рассуждением оценивает по критерию, второе мнение даёт расхождение, код проверяет основания, эталон с порогами ловит регресс по языкам и грубым ошибкам. Свои веса не обучаем: на 65 диалогах это шум, а новый критерий после стоп-кода классификатор не возьмёт. Дорожная карта для прода: кластеризация причин по смыслу и контроль дрейфа доли отмен на тысячах диалогов, дистилляция накопленной разметки в дешёвый классификатор для простых случаев, очередь проверки по уверенности.

### Запуск агента Claude (Opus)

Оркестратор запускает субагента через `Agent` с `isolation: "worktree"` и промптом:

```
Прочитай AGENTS.md. Выполни /opsx:apply <change>, только группу <N>.
TDD: тест, красный прогон, код, зелёный прогон. После каждой задачи make check, коммит, push.
Первый push: gh pr create --draft --fill. Когда группа готова: rebase на origin/main, make check, gh pr ready.
Отчёт: номер PR, что сделано, что не прошло.
```

### Запуск агента pi (GLM)

```bash
scripts/wt.sh new <change> <slug>
cd .worktrees/<change>-<slug>
pi -p --no-session --no-extensions --approve --model zai/glm-5.3 --thinking high \
  "Прочитай AGENTS.md и .pi/prompts/opsx-apply.md и действуй по нему для изменения <change>, только группа <N>. TDD, make check перед каждым push, PR как в AGENTS.md." \
  </dev/null > ../<change>-<slug>.log 2>&1 &
```

Для мелких задач модель `zai/glm-5.3-flash`. Одновременно не больше 8 агентов pi. `--no-extensions` отключает расширение разрешений, которое иначе ждёт ответа человека бесконечно. `--approve` разрешает читать файлы проекта. Шаблон `opsx-apply` агент читает как файл: подстановка шаблонов в режиме `-p` не гарантирована.

Волна 0 стартует до появления `scripts/wt.sh`, поэтому её worktree оркестратор создаёт вручную:

```bash
git fetch origin main
git worktree add .worktrees/bootstrap-harness-core -b feat/bootstrap-harness-core origin/main
for p in openspec AGENTS.md CLAUDE.md .claude .pi; do ln -s "$PWD/$p" ".worktrees/bootstrap-harness-core/$p"; done
```

### Ревью и слияние

```bash
gh pr list --state open                       # доска PR
gh pr diff <n> | head -400                    # ревьюер другой модели читает изменения
gh pr review <n> --comment --body "..."       # замечания
gh pr checks <n>                              # CI зелёный?
gh pr merge <n> --squash --delete-branch      # сливает только оркестратор
scripts/wt.sh rm <change> <slug>              # убрать worktree
openspec archive <change>                     # после последней группы изменения
```

### Доска статуса

`openspec list` показывает прогресс задач по изменениям, `gh pr list` — открытые PR, `gh run list` — CI. Оркестратор раз в 30 минут сверяет доску с контрольными точками и перебрасывает агентов на отстающий трек.
